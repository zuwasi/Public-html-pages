Implications
IMPLICATIONS FOR ARDUPILOT

Real critical bugs surfaced by the benchmark

A single LAN-adjacent attacker can take over an ArduPilot vehicle in flight. The benchmark surfaced six distinct paths to that outcome.

Unauthenticated DDS (ROS 2 over UDP:2019)

  • ARM / DISARM service — no auth
  • MODE_SWITCH service — no auth
  • TAKEOFF service — no auth
  • SET_PARAMETERS service — disables ARMING_CHECK, FENCE_ENABLE, SCR_ENABLE
  • Joy topic — overrides all RC channels

CVSS up to 10.0. libraries/AP_DDS/AP_DDS_Client.cpp

MAVLink subsystem

  • MAVFTP arbitrary file r/w + .. traversal
  • MAVFTP → drop Lua script in APM/scripts/ → RCE
  • SERIAL_CONTROL → drive any UART (ESC, GPS, modem, bootloader)
  • @SYS/storage.bin exfiltrates MAVLink signing key

CVSS 9.6. GCS_FTP.cpp · GCS_serial_control.cpp

Signed-firmware fail-open

  • check_signature() returns true when all bootloader public keys are zero
  • SETUP_SIGNING accepted before signing is provisioned

CVSS 9.1. AP_CheckFirmware_secure_command.cpp:199

Memory-safety cluster

  • handle_device_op_write — 127-byte OOB read
  • @SYS lseek signed/unsigned OOB read
  • Param upload OOB + biased AP_Param writes
  • apfs_fgets int → uint8 truncation

CVSS 4 – 7. Surfaced uniquely under main_prompt.txt.

Planned fixes
WHAT WE PLAN TO FIX

Ordered by leverage

1 · Make MAVLink signing mandatory

Gate FILE_TRANSFER_PROTOCOL, SERIAL_CONTROL, SECURE_COMMAND, and PARAM_SET behind signing_enabled() in shipped builds. Default GCS_SYSID_ENFORCE = 1.

2 · Apply DDS-Security profile

Authentication + access control + encryption on UDP:2019. Until then, bind the DDS transport to 127.0.0.1 and require an authenticated tunnel (WireGuard / IPsec) between vehicle and companion computer.

3 · Remove the fail-open in check_signature

Delete the if (all_zero_keys(...)) return true; branch. If no keys are provisioned, refuse SECURE_COMMAND entirely. Provisioning must happen over USB + serial console only.

4 · Allowlist MAVFTP paths

Resolve request.data with realpath and reject anything outside /APM, /@SYS, /@PARAM, /@MISSION, /@ROMFS. Block .. segments after normalization.

5 · Sign Lua scripts

Refuse to load unsigned .lua from APM/scripts/ when the script was written within the current boot via a non-USB transport.

6 · Memory-safety patches

Fix handle_device_op_write bounds, @SYS lseek, apfs_fgets truncation, and the param-upload OOB. Add unit tests.

Items 1 – 3 alone collapse every Critical finding in this benchmark.

Upstream reality
DON'T BOTHER · WONTFIX

Real risks that match ArduPilot's stated design

ArduPilot's threat model is explicit: MAVLink and DDS run on operator-trusted links. Authentication, isolation, and link security are the operator's job, not the firmware's. PRs that "add auth" to these transports are closed as WONTFIX.

MAVFTP unauth + .. traversal

Upstream answer: "Use SETUP_SIGNING and set GCS_SYSID_ENFORCE = 1. Operators choose their radio link." Path normalization is rejected because it would break legitimate uses of @SYS, @PARAM, and operator-relative FTP scripts.

Unauth DDS ARM / MODE / TAKEOFF / SET_PARAMETERS

Upstream answer: "DDS is for trusted LAN segments and companion computers. Deploy the DDS-Security profile or isolate the network. The protocol is designed for high-rate, low-overhead intra-vehicle messaging — auth checks per packet are a non-starter."

SERIAL_CONTROL unauth UART passthrough

Upstream answer: "It is intentional — that's how operators flash GPS firmware, talk to ESCs, and debug bootloaders. Require signing if you don't trust the link." Adding always-on gating breaks every existing ground-station workflow.

DDS Joy topic overrides RC channels

Upstream answer: "RC_Channels::set_override is the canonical RC-failsafe mechanism; the Joy topic is the documented ROS 2 interface for external control." Removing it would break MoveIt, Nav2, and Gazebo integrations.

✓ What CAN get merged: opt-in hardening parameters

  • New FTP_OPTIONS bitmask with FTP_REQUIRE_SIGNING and FTP_ALLOWLIST_PATHS bits
  • New DDS_AUTH_MODE parameter — reject ARM / MODE / TAKEOFF unless the origin is authenticated
  • New SERIAL_PASS_REQUIRE_SIGNING bit in SERIAL_PASS

These don't change default behavior (which maintainers value) but give security-conscious operators — medical, defense, commercial fleet — a switch to flip.

Strategy: ship the 7 memory-safety / fail-open patches as straight bug-fix PRs, then open RFC PRs for the opt-in hardening switches.

FIX #1 · CWE-305 · SIGNED-FIRMWARE FAIL-OPEN

check_signature() bootstrap-only carve-out

libraries/AP_CheckFirmware/AP_CheckFirmware_secure_command.cpp

Before

bool AP_CheckFirmware::check_signature(
        const mavlink_secure_command_t &pkt)
{
    const struct ap_secure_data *sec_data =
        find_public_keys();
    if (sec_data == nullptr) {
        return false;
    }
    if (all_zero_keys(sec_data)) {
        // allow through if no keys are setup
        return true;       // ◀ FAIL-OPEN
    }
    if (pkt.sig_length != 64) {
        return false;
    }
    ...
}

Every operation passes when keys are zero — including GET_SESSION_KEY, REMOVE_PUBLIC_KEYS, and any future op.

After

bool AP_CheckFirmware::check_signature(
        const mavlink_secure_command_t &pkt)
{
    const struct ap_secure_data *sec_data =
        find_public_keys();
    if (sec_data == nullptr) {
        return false;
    }
    if (all_zero_keys(sec_data)) {
        // only allow bootstrap op
        return pkt.operation ==
            SECURE_COMMAND_SET_PUBLIC_KEYS;
    }
    if (pkt.sig_length != 64) {
        return false;
    }
    ...
}

First-time provisioning still works. Every other op (including additional SET_PUBLIC_KEYS after first install) requires valid Ed25519 signature.

Threat closed: attacker on a MAVLink-reachable interface against a board built with AP_SIGNED_FIRMWARE but never provisioned (or wiped via REMOVE_PUBLIC_KEYS) can no longer install their own keys, exfiltrate the would-be session key, or flash signed bootloader payloads.

FIX #2 · CWE-125 · DEVICE_OP_WRITE OOB READ

handle_device_op_write() count bound check

libraries/GCS_MAVLink/GCS_DeviceOp.cpp

Before — read handler has it

// handle_device_op_READ() — line 56
if (packet.count > sizeof(data)) {
    retcode = 5;
    goto fail;
}                // ◀ check exists

// handle_device_op_WRITE() — line 122
if (!dev->get_semaphore()->take(10)) {
    retcode = 3;
    goto fail;
}
if (packet.regstart == 0xff) {
    dev->transfer_bank(packet.bank,
        packet.data, packet.count, ...);
} else {
    for (uint8_t i=0; i<packet.count; i++) {
        dev->write_bank_register(packet.bank,
            packet.regstart+i,
            packet.data[i]);  // ◀ OOB
    }
}

packet.count is uint8_t (max 255), packet.data is 128 bytes. Stack contents leak onto the I2C/SPI bus.

After

// handle_device_op_WRITE()
if (!dev) { retcode = 2; goto fail; }

if (packet.count > sizeof(packet.data)) {
    // bound count against payload
    // buffer to prevent OOB read
    // from packet.data[i] in the
    // register write loop and OOB
    // read in transfer_bank() below.
    retcode = 5;
    goto fail;        // ◀ added
}

if (!dev->get_semaphore()->take(10)) {
    retcode = 3;
    goto fail;
}
// ... rest unchanged ...

Mirrors the existing check in the read handler. 7 lines added, zero deletions.

Threat closed: a malicious or buggy GCS can no longer push 127 bytes of stack contents onto a hardware bus or corrupt arbitrary peripheral register space via DEVICE_OP_WRITE.

FIX #3 · CWE-125 · @SYS LSEEK WILD OOB READ

AP_Filesystem_Sys::lseek() signed/unsigned safety

libraries/AP_Filesystem/AP_Filesystem_Sys.cpp

Before

int32_t AP_Filesystem_Sys::lseek(
    int fd, int32_t offset, int seek_from)
{
    ...
    struct rfile &r = file[fd];
    switch (seek_from) {
    case SEEK_SET:
        r.file_ofs = MIN(offset,
            (int32_t)r.str->get_length());
        break;   // ◀ -1 → 0xFFFFFFFF
    case SEEK_CUR:
        r.file_ofs = MIN(r.str->get_length(),
            offset + r.file_ofs);
        break;   // ◀ same hazard
    case SEEK_END:
        errno = EINVAL;
        return -1;
    }
    return r.file_ofs;
}

// later, read() does:
count = MIN(count, get_length()-file_ofs);
memcpy(buf, get_string()+file_ofs, count);
//     ◀ wild address when file_ofs=0xFFFFFFFF

After

case SEEK_SET:
    // reject negative absolute offset
    if (offset < 0) {
        errno = EINVAL;
        return -1;
    }
    r.file_ofs = MIN(
        (uint32_t)offset, length);
    break;

case SEEK_CUR: {
    // compute in int64_t, detect
    // under/overflow, then clamp
    const int64_t new_ofs =
        (int64_t)r.file_ofs +
        (int64_t)offset;
    if (new_ofs < 0) {
        errno = EINVAL;
        return -1;
    }
    r.file_ofs = MIN(
        (uint32_t)MIN<int64_t>(
            new_ofs, length),
        length);
    break;
}
case SEEK_END:
    errno = EINVAL;
    return -1;

Threat closed: over MAVFTP, any client could request OpenFileRO /@SYS/storage.bin (or flash.bin) and lseek to a negative offset. The buffer base is the live EEPROM pointer or 0x08000000 internal flash — the attacker could read MAVLink2 signing keys and arbitrary firmware bytes. With this fix, negative offsets return EINVAL.
