The problem, concretely

MISRA C:2025 Rule 7.5 (Mandatory)

"The argument of an integer constant macro shall have an appropriate form." One coding habit, repeated everywhere, produces easily identifiable violations: negative values or suffixes placed inside the macro.

NONCOMPLIANT 
/* Negative or suffixed argument */
#define TEMP_OFFSET   INT32_C(-40)
#define MIN_PRESSURE  INT32_C(-100)
#define MASK          UINT32_C(0xFFUL)
COMPLIANT 
/* Minus outside, no suffix */
#define TEMP_OFFSET   (-INT32_C(40))
#define MIN_PRESSURE  (-INT32_C(100))
#define MASK          UINT32_C(0xFF)

Because the same pattern repeats at every #define and every call site, it is mechanically findable and mechanically fixable. That is exactly what tooling is for.

Steps 1 and 2 · Sourcegraph

Inventory every violation class with scoped queries

repo:^github\.com/our-org/(repoA|repoB|repoC|repoD)$
  (U?INT(?:8|16|32|64))_C\(\s*-\s*[0-9]+\s*\)
  patternType:regexp lang:C lang:C++ count:5000

Pattern 1

Negative argument, decimal: INT32_C(-40). Minus moves outside the macro.

Pattern 2

Suffix inside macro, decimal or hex: UINT32_C(0xFFUL). Suffix stripped.

Pattern 3

Non-literal argument: INT32_C(SOME_MACRO). Flagged for human decision, never auto-fixed.

Queries also match call sites like set_trim(INT32_C(-25)), not only #define lines. Release branches are covered with Sourcegraph revision syntax, so nothing hides on the other 399 branches.

Steps 3 and 4 · Sourcegraph Batch Changes

Thousands of fixes, one reviewed pull request per repo

What the automation applies

INT32_C(-40)   →  (-INT32_C(40))
INT32_C(-100)  →  (-INT32_C(100))
UINT32_C(100U)  →  UINT32_C(100)
UINT32_C(0xFFUL) →  UINT32_C(0xFF)
INT64_C(-500)  →  (-INT64_C(500))

What management sees

Not a black box: Batch Changes opens standard pull requests. Every change is a visible diff, reviewed by the team like any other code change, applied with the same CI checks.

Dry-run preview first, publish on approval. The changeset flows to all branches through normal merge, keeping the fix set consistent without touching 400 branches by hand.

Value-preserving by construction: the numeric value never changes, only its form. The compiler and CI protect against anything the automation gets wrong.

Safety rails

Automation knows what not to touch

Signed minimum: INT32_MIN

INT32_C(-2147483648) cannot become (-INT32_C(2147483648)), because 2147483648 does not fit in a 32-bit signed type. The compliant form is ((-INT32_C(2147483647))-1). The automation excludes it; an expert fixes the handful of cases.

Range checks after suffix removal

The argument must fit the macro's type. Values that were already out of range are surfaced by the scanner as compile-time findings, which is the correct, early signal.

Human-review list, never auto-fixed

Non-literal arguments such as INT32_C(OTHER_MACRO) or INT32_C(2+3) are collected in a short manual list. Deliberately small and expert-owned.

Full review before merge

The Batch Change ships as an unreviewed draft by default. Nothing merges until the team signs off, and CI must pass on every repo.

Steps 6 and 7 · Closing the loop

PROOF 1 · SOURCEGRAPH

The finder becomes the auditor

Re-running the exact queries from step 1 must return zero results on all repos and indexed branches. Source-level absence of the pattern, confirmed in seconds, any time.

PROOF 2 · PARASOFT

The scanner certifies it

A full Parasoft C/C++test scan of the whole project reports zero Rule 7.5 findings. This is the compliance evidence of record for auditors and certification.

After cleanup, the same search runs in CI as a guard: any new violation of the pattern is caught at the pull request that introduced it, before it spreads to branches. The scanner runs on the merged result. Zero violations become the steady state, not a one-time achievement.
