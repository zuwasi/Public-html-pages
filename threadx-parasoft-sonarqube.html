Where the defect inputs come from

Trigger data arrives from queue receives (tx_queue_receive into caller memory) and from volatile simulated sensor registers. At runtime the producer only writes documented in-range values, so the application keeps running; statically, a cross-thread queue payload is an unknown value and a volatile read is a fresh unknown.

Runtime-benign by design. A 20-second soak ran with all 52 plants present and the process stayed alive. That establishes only that — it is not proof that every defect is harmless, and the deck never treats it as such.

06 · Method

How the defects were built to be hard, and fair

design intent, stated in advance
not tuned after the scan
1 · Flow-analysis grade

Candidates need interprocedural, path-sensitive or dataflow reasoning — a guard that is not exhaustive, a contract the caller ignores, ownership that crosses a function boundary. Rule-matching alone does not reach most of them.

2 · Runtime-benign, statically reachable

Defect branches depend on error paths that never fire under the harness's runtime conditions (queue full, allocation failure, abort request), so the demo keeps running while every defect stays reachable in the analysis.

3 · No constant-propagation give-aways

Bounds checks that exist use live values, and defect inputs come from volatile registers or cross-thread queue payloads that cannot be folded to a constant.

4 · ThreadX realism

Defects sit inside a real sensor-telemetry pipeline built from the same primitives real firmware uses. Candidates marked [TX] additionally require modeling ThreadX semantics — pool lifecycle, mutex ownership, kernel-object create/delete. These probe depth, not pattern coverage.

5 · Size arithmetic emphasized

12 candidates: truncation, wrap, signed/unsigned conversion, sizeof(pointer) misuse, masked-length checks, off-by-one. This is the family the report reads first, and the one the deck shows most code for.

Runtime inputs, documented per defect

The catalog states what the producer actually writes for each trigger (for example g_sensor_count = tx_time_get() & 0xF, so 0–15). That is how "hard statically, benign at runtime" is verified rather than asserted.

Why this matters when reading the results. A defect that a tool misses here is one that needs flow reasoning, not one that is unreachable or hidden behind a constant. The rules and the profiles used to attack the set are on slide 20.

Why the concurrency family is the sharpest test

All four threads are created with tx_thread_create inside harness_init.c. A tool that does not model ThreadX thread creation cannot see that the functions run concurrently at all, and the eight races become invisible rather than merely hard.

The [TX] candidates

Eight candidates additionally require ThreadX API semantics: byte-pool memory is not zeroed, a block-pool block must be released with tx_block_release, a mutex put requires ownership, a created TX_TIMER must be deleted. They probe RTOS knowledge rather than pattern coverage.

Compiler-visible controls

Two plants (BUG-008, BUG-048) are things MSVC itself warns about — C4700 class defects. They are useful as a floor: any flow analyzer that misses the compiler-visible cases would be reported as such.

What is wrong

Both expressions come from the same value through different routes. For any count above 16383 the truncated 16-bit size is smaller than the copy, so the heap buffer is overrun.
