What SWE-sweep is

SWE-sweep is a benchmark from Meta Superintelligence Labs (Lieret et al., ICLR 2026 preprint, facebookresearch/swe-sweep). It asks a harder question than SWE-bench: not "fix this reported issue" but "an agent is given a real repository containing an unknown number of confirmed bugs and no hints. How many can it find and fix?"

  • 100 repositories, 4,100 bugs. Each repo snapshot is a commit where the maximum number of upstream-confirmed bugs coexist.
  • No hints. No issue text, no filenames, no line ranges. The agent must explore, hypothesize and repair on its own.
  • Unforgiving scoring. Each candidate fix runs against hidden fail-to-pass tests from the upstream pull request, plus the repository's entire existing test suite. A single regression zeroes the whole repo reward.

The official leaderboard is sobering: the best entry in the world, GPT-5.6 Sol on the minimal mini-SWE-agent scaffold, resolves 4.7% of the bugs for $7,230 per full run. Most entries sit between 0.1% and 2.5%.

What the benchmark's authors say about harnesses

SWE-sweep's FAQ directly addresses whether the agent scaffold matters:

“Our paper has an ablation with Claude Code and Codex. Neither seems to significantly outperform mini-swe-agent (to the contrary, mini-swe-agent is even quite a bit better than Codex).”SWE-sweep FAQ, swesweep.com, accessed October 21, 2026

The academic context agrees that the loop around the model carries much of the outcome: the SWE-agent ACI ablation moved resolution from 3.8% to 12.5% with no new weights (NeurIPS 2024); a 2026 survey, Code as Agent Harness (arXiv:2605.18747), names "harness-level evaluation" the field's open problem #1; and Kaggle's 2026 SDLC analysis attributes roughly 90% of an agent's engineering to the harness, 10% to the model.

Our experiment: hold the model, vary the harness

We built a small harness (github.com/zuwasi/mini-swe-sweep) that gives both agents identical treatment:

  • Two arms, one model: Amp (default mode) and Claude Code (headless defaults), both running claude-opus-5-5. The harness is the only variable.
  • 12 repositories spanning C, C++, C#, F#, Java, Python and Rust: libexpat, click, gson, roslyn, z3, tokio, hdf5, proj, black, rxjava, fsharp, syn.
  • 5 frozen reference bugs per repo, 60 scored tasks, a 60-minute cap per session, and the official SWE-sweep Docker verifiers as the only referee. The agents never see the tests.
# run_agent.sh (core): identical loop for both CLIs
cd "$REPO" && timeout 3600 "$AGENT_CLI" < prompt.md > session.log
git diff > "patches/${AGENT}__${REPO}.diff"

# eval.sh: replay into the official SWE-sweep task image
run_verifier "$TASK_DIR" --patch "patches/${AGENT}__${REPO}.diff"

Amp resolved bugs in 4 of 12 repos (click, gson, proj, rxjava); Claude Code in 2 (tokio, rxjava). Amp finished all 12 sessions inside the one-hour cap. Three Claude Code sessions ended when the tool hit its own plan spend limit; the patches those sessions produced were still graded by the real verifier. The full per-run table with durations, patch sizes and verifier JSONs is on the public results page.

Honesty clause: one resolved bug is worth 1.67 points on our 60-bug subsample, so 4-vs-2 is directional evidence, not a statistical proof. It aligns, however, with our earlier quantum-kernel study, where the same pattern appeared at much larger effect size.

What they failed, and why it matters

On z3, Amp spent the full hour and produced a 399-line patch of plausible API-mapping fixes. Every hidden test still failed; the reward was 0.0. Claude Code wrote 1,006 diff lines on the same repo and also scored 0. On behavioral solver bugs, plausible is not passing, and more output is not more resolution.

On roslyn, the regression gate earned its keep. Amp's patch resolved a bug but swapped the synthesized hash-function names for Span and ReadOnlySpan pattern matches, breaking an existing test:

# verifier/reward.json for amp/roslyn
{ "reward": 0.0, "n_resolved": 0.0, "visible_ok": 0.0, "n_regressions": 1.0 }

SWE-sweep scores the patch, not the intention. This is exactly the fence production agent use needs, and it is a harness property, not a model one.

The Parasoft C++test control: 0 to 0.3%

Before crediting agents, we asked whether classic static analysis finds these bugs at all. On six C/C++ repos (libexpat, jerryscript, hdf5, proj, z3, tarantool) we ran Parasoft C++test Professional 2025.2.0 in five configurations: Recommended Rules, Flow Analysis Standard, Flow Analysis Aggressive, MISRA C 2025 and MISRA C++ 2023. That produced roughly 500,000 findings. We then checked each finding against the SWE-sweep oracle patches: a finding "hits" a bug only if its line falls on a line the upstream fix changed.

Wherever a fair baseline exists, the hit rate sits at or below the random density of changed lines. The apparent jerryscript overlap is a line-density artifact, not detection. This is expected once you look at what the bugs are: a null re-entry in an RxJava operator, an overflow in a Rust size_hint, a swapped hash-function name in a C# compiler backend. These are semantic, behavioral defects judged by hidden tests, not pattern violations a rule can name.

The conclusion is complementary, not competitive. For MISRA/CERT/AUTOSAR compliance work, static analysis is the right instrument and ESL deploys it daily. For unreported behavioral bugs, the agent loop wins, and the published direct-LLM baseline in the same study (no agent loop) resolves only 0 to 20% per repo. Our pipeline recommendation: static analysis for the rule book, agents for behavior, hidden tests as the referee.

Why the harness is the king

This is our second controlled harness study. The first, on four from-scratch quantum-compiler C++ kernels (qubit routing, magic-state scheduling, GRAPE pulse control, tensor contraction), put Amp's fast tier against Claude Code running the era's strongest model at maximum reasoning effort:

TaskAmp (rush)Claude Code + Fable 5 (max)Cost ratio
Qubit routing (NP-complete)1.0000.88962×
All 4 tasks1.000, $1.930.972, $75.4039×

Two independent benchmarks, different task domains, different model classes, one direction: the same weights produce very different software depending on the loop you wrap around them. The deciding harness behaviors in the SWE-sweep runs were repo-wide context management, knowing when to stop exploring and edit, patch-size discipline, and running the visible test suite before declaring victory. None of those live in the model.

That is why we say the harness is the king, and why the winner of this benchmark is Amp: twice the resolved bugs of Claude Code on identical weights, every session completed inside the cap, minimal targeted diffs, a score above the best official full-run entry, and a prior study showing the same pattern at 39× lower cost. Claude Code's harness earns real credit too; it found tokio, which Amp missed. But on the evidence we collected, Amp built the better loop.
