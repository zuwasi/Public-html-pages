THE BENCHMARK · 02

What is SWE-sweep?

Meta Superintelligence Labs: can agents autonomously find and fix bugs in large codebases?

  • 100 real repositories, 4,100 confirmed bugs. Built from issue–pull request pairs; each repo snapshot is a commit where the maximum number of bugs coexist.
  • Open-ended task. The agent gets the repository at a fixed base commit and one broad instruction: find and fix as many bugs as you can. No issue text, no filenames, no line ranges, no hints.
  • Brutal scoring. Every candidate fix runs against hidden fail-to-pass tests from the upstream PR, plus the repository's whole existing test suite. One regression zeroes the repo's reward.
  • ICLR 2026 preprint by Lieret, Ma, Wei, Yang, Press and colleagues at Meta Superintelligence Labs, Harvard, UW and Stanford.
issue + PR pairs ──► find commit where many bugs coexist ──► repo snapshot at base commit │ │ ▼ ▼ hidden fail-to-pass tests agent explores, no hints, fixes bugs (from the upstream fix) outputs one patch for the whole repo │ │ ▼ ▼ regression gate: original test suite must still pass ──► reward = bugs resolved / 4100
Paper and leaderboard: swesweep.com · Source: github.com/facebookresearch/swe-sweep
THE BENCHMARK · 03

How a bug is scored

Two test sets per bug, and a gate that punishes collateral damage

  • A bug counts only if every hidden test for it passes and the untouched upstream test suite still passes.
  • The agent is explicitly told to avoid regressions. Breaking existing behavior on one line can erase a correct fix elsewhere in the same repo.
  • This is why a plausible-looking 400-line patch can score exactly 0.

THE BENCHMARK · 05

What the authors say about harnesses

From the official SWE-sweep FAQ: does the scaffold matter?

“Why mini-swe-agent? Could other scaffolds/multi-agents achieve higher performance? Our paper has an ablation with Claude Code and Codex. Neither seems to significantly outperform mini-swe-agent (to the contrary, mini-swe-agent is even quite a bit better than Codex).” SWE-sweep FAQ, swesweep.com, accessed October 21, 2026
  • The benchmark's own authors found harness choice does not separate the big scaffolds at their resolution: Claude Code, Codex and mini-swe-agent land in the same band.
  • That is exactly the question we set out to test at ESL, but head to head, same model, production harnesses, with the SWE-sweep verifier as the referee.
  • And note rank 5: Opus 5 (xhigh) in the mini-swe-agent harness scores 1.3%, while the same Opus-class model in Amp's harness scored multiples of that in our runs.

OUR EXPERIMENT · 07

The question: same model, different harness

If two production agent harnesses run the identical LLM, does the harness decide the outcome?

  • Arm 1: Amp (default mode), headless, one prompt per repo.
  • Arm 2: Claude Code (headless defaults), identical prompt.
  • Identical model: claude-opus-5-5 on both arms. The harness is the only variable.
  • 12 repositories across C, C++, C#, F#, Java, Python and Rust: libexpat, click, gson, roslyn, z3, tokio, hdf5, proj, black, rxjava, fsharp, syn.
  • 5 frozen reference bugs per repo = 60 scored tasks.
  • 60-minute cap per agent-repo session, enforced by the harness.
  • Official SWE-sweep Docker verifiers score every patch. No self-grading anywhere.
Harness, logs and patches: github.com/zuwasi/mini-swe-sweep

What the agents got right: click (Python)

Amp, 80-line patch, scored 1/5: two Python 3 API bugs in the bundled examples

  • Small, surgical, exactly at the failing lines. The hidden tests passed and the original suite stayed green.
  • This is the harness discipline pattern we see across all four Amp wins: locate, minimally fix, stop.
BUG CASE FILES · 12

Claude Code's wins: tokio (Rust)

A real, minimal, correct fix. The harness found it; the model wrote it.

  • Two latent bugs in one patch: the macro's requires-argument list was missing "crate", and size_hint could overflow on huge stream maps.
  • 553 diff lines total, scored 1/5 on the hidden tests with a clean regression gate.
BUG CASE FILES · 13

Claude Code's wins: rxjava (Java)

The original code called onError(null) recursively, re-entering the null branch forever

  • The bug: onError(e) with e == null builds a NullPointerException and passes it back through onError(null), recursing instead of storing it.
  • The fix assigns the exception instead of recursing. One line, judged by hidden behavioral tests. This is the exact bug class where the Parasoft control found zero coverage (slide 19).
BUG CASE FILES · 14

What the agents failed: z3 (C++), 399 lines, scored 0

Amp burned the full hour, produced a plausible 399-line patch, and every hidden test still failed

  • exit code 124: the 1-hour cap expired mid-exploration. The bug surface (string theory solver internals) needed longer-horizon search than either arm got.
  • Claude Code wrote 1,006 diff lines on z3 and also scored 0. On these behavioral solver bugs, more output is not more resolution.
  • Failure mode: exploring a 100k-line C++ codebase without a falsifiable hypothesis per edit. The hidden tests never got a chance to pass.
BUG CASE FILES · 15

The regression gate: roslyn (C#), zeroed

One resolved bug, one broken existing test, reward 0.0

  • SWE-sweep scores the patch, not the intention. A fix that passes hidden tests but breaks the existing suite earns nothing.
  • The same gate zeroed a Claude Code roslyn diff with 22 regressions in our earlier cost-tier run.
  • Lesson for production agent use: always run the agent inside a regression-gated loop. Both harnesses needed the fence.

CONTROL STUDY · 17

The Parasoft C++test control

Before crediting agents, we asked: can classic static analysis find these bugs at all?

  • Tool: Parasoft C++test Professional 2025.2.0, licensed, run on 6 C/C++ SWE-sweep repos: libexpat, jerryscript, hdf5, proj, z3, tarantool.
  • Five configurations: Recommended Rules, Flow Analysis Standard, Flow Analysis Aggressive, MISRA C 2025, MISRA C++ 2023.
  • ~500,000 findings in total across the configurations.
  • Ground truth: the SWE-sweep oracle patches. A finding "hits" a bug only if its line falls on a base-side line that the upstream fix actually changed.

CONTROL STUDY · 19

Why static analysis is not relevant to SWE-sweep

And why it is still not the loser of this story

Different question, different tool

  • SWE-sweep scores behavioral regressions: a null re-entry in an RxJava operator, a swapped hash-function name in a C# compiler backend, an overflow in a Rust size_hint. Each needs semantics, intent, and a failing test to reason from.
  • Static analysis checks patterns and invariants reachable from syntax and dataflow. It cannot know that ret.0 += hint.0 is wrong here but right everywhere else.
  • Look at the rxjava fix on slide 13: one line, judged by hidden behavioral tests. No rule in ~500,000 findings describes that contract.

Complementary, not competing

  • For safety-critical work (ESL's home turf: MISRA, CERT, AUTOSAR), C++test is exactly the right tool and we deploy it daily.
  • For "find the bugs nobody reported yet", the agent loop wins, and the published direct-LLM baseline in the same study (no agent loop) resolves only 0 to 20% per repo.
  • The pipeline we recommend to clients: static analysis for the rule book, agents for the behavior, hidden tests as the referee.
This control study is why the agent results mean something: the SWE-sweep bugs are genuinely hard, and no cheaper classical instrument detects them.
ANALYSIS · 20

Why the harness is the king

The same weights, two different products, two different outcomes

┌──────────────────────────────────────────────┐ │ coding agent product │ │ ┌────────────┐ ┌───────────┐ ┌───────────┐ │ │ │ UI / CLI │ │ orchestr. │ │ context + │ │ │ │ 5% │ │ 15% │ │ index 15% │ │ │ └────────────┘ └───────────┘ └───────────┘ │ │ ┌────────────┐ ┌───────────┐ ┌───────────┐ │ │ │ tools + │ │ verify │ │ memory + │ │ │ │ shell 20% │ │ 20% │ │ guard 10% │ │ │ └────────────┘ └───────────┘ └───────────┘ │ │ ┌──────────────────────────────────────┐ │ │ │ LLM core: 15% │ │ │ └──────────────────────────────────────┘ │ └──────────────────────────────────────────────┘
  • The model is the engine. The harness is the car. Nobody commutes to work on an engine.
  • In our SWE-sweep runs the deciding harness behaviors were: repo-wide context management, when to stop exploring and edit, patch-size discipline, and running the visible test suite before declaring victory.
  • The models are converging. The scaffolding is diverging. That is where evaluators, buyers and builders should look.

CONCLUSION · 21

The winner: Amp

On this benchmark, with the model held constant, the harness with the better loop won. Twice.

  • 2× the resolved bugs on identical weights: 4/60 (6.7%) vs Claude Code's 2/60 (3.3%), same model, same prompt, same cap, same verifier.
  • Above the state of the art: 6.7% on our subsample vs 4.7% for the best official full-run entry, which cost $7,230.
  • Cleaner cost profile: Amp completed every session inside the cap and produced minimal, targeted diffs; Claude Code needed larger patches for fewer wins and lost three sessions to its own spend limit.
  • Consistent with our prior study: on the quantum-compiler kernels, Amp solved 4/4 where max-effort Claude Code stopped at 3/4, at 39× lower cost.
  • The compliment that matters: Amp's context handling, tool execution and verification loop turn the same engine into measurably more working software. The harness is the product, and Amp built a better one.
CONCLUSION · 22

Honest limitations

A benchmark you can trust names its own boundaries first

  • n = 60, one seed. One bug equals 1.67 points, so 4-vs-2 is directional evidence, not a statistical proof. It aligns with two independent studies pointing the same way.
  • Subsample: 5 frozen reference bugs per repo, not the full 4,100. Our percentages are placement estimates against official full runs.
  • Quota endings: three Claude Code sessions ended at the plan spend cap. Their patches were graded by the real verifier, but those sessions had less effective exploration time.
  • Costs are estimates from measured wall time, not vendor invoices; token-level attribution is not exposed by either CLI.
  • Both harnesses are good. Claude Code resolved bugs Amp missed (tokio). This is a ranking on one benchmark slice, not a verdict for all workloads. Run candidates on your own code.
CONCLUSION · 23

What to do Monday

Buy the harness, not the leaderboard

  • Stop shopping for the biggest model. The same model scored 1.3%, 3.3% or 6.7% depending on the loop you put around it.
  • Evaluate harnesses on your repos: context management, tool execution, verify loops, spend discipline, regression fences.
  • Keep static analysis for the rule book and compliance; keep agents for behavioral bugs; keep hidden tests as the only referee.
  • Budget the plan limit, not just the tokens: quota interruptions cost us five Claude batch attempts before we stabilized the protocol.
