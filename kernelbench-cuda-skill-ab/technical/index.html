The question · 02

Three candidate benchmarks, one runs on this laptop

The selection criterion was brutal and simple: the benchmark must execute on a 16 GB consumer Blackwell GPU in WSL2 without renting cloud silicon

Pilot design

KernelBench, subset, both conditions

4 problems spanning the performance regimes: memory-bound reduction (Softmax, sum reduction), compute-bound GEMM (square matmul), and a Level-2 fusion chain (GEMM + multiply + LeakyReLU).

Metric contract

fast_p simplified: correct and faster

A solution scores only if it passes allclose(rtol=1e-2, atol=1e-2) on multiple seeds against the PyTorch reference; the reported number is the median speedup ratio.

Benchmark triage from the maintainer documentation of all three projects; selection made before any code was written.
The machine · 03

One consumer Blackwell GPU, one WSL2 host, zero cloud

Everything ran on the laptop the pilot owns: the same machine that browses email also compiled and timed every kernel

GPU

NVIDIA GeForce RTX 5080 Laptop, Blackwell, 16 GB GDDR7, 55 W power cap (80 W default); this detail shapes the whole methodology

Stack

Environment bring-up, measured
  • uv venv --python 3.10 + uv sync: 22 min, dominated by the CUDA wheel set
  • load_inline first compile per extension: 30-90 s (nvcc, arch=compute_120,code=sm_120)
  • Build cache ~/.cache/torch_extensions makes later iterations near-instant; the skill teaches agents to keep CUDA source stable to reuse it
The constraint that defines the methodology

At a 55 W cap the GPU dynamically throttles: SM clocks observed as low as 180 MHz, and the reference softmax measured 55.9 ms in one session and 716.7 ms in another. Sequential A-then-B timing is worthless on this machine; the pilot's protocol uses interleaved ref/candidate timing to cancel it (slide 09).

The intervention · 04

The super skill: three sources fused into one loop

cuda-kernel-super did not exist; no CUDA optimization skill was installed. It was built the morning of the pilot from researched public material plus machine-specific truths

  · arch flag compute_120/sm_120 (a silent failure otherwise)
  · interleaved ref/cand timing (the 55 W throttle)

What was deliberately left out

Hugging Face cuda-kernels (HF Hub packaging, irrelevant to KernelBench), NVIDIA TileGym (cuTile-DSL only), and KernelFlow's heavyweight orchestration scripts (geared to optimizing an existing kernel with fixed dims, not writing one from a problem statement). The skill keeps the methodology, not the machinery.

Skill anatomy

SKILL.md (workflow, contract, checklist) + reference/techniques.md (bottleneck → technique catalog with CUDA snippets) + reference/pitfalls.md (failure modes that waste turns) + scripts/bench.py (the honest evaluator itself ships with the skill).

Skill sources: KernelFlow-ops/cuda-optimized-skill (MIT), ScalingIntelligence/KernelBench docs, and measurements taken on this machine during setup.
Inside the skill · 05

The technique catalog: bottleneck first, cleverness second

The skill forces an analysis step before any code: classify the op's regime, compute the roofline, and only then pick techniques in expected-impact order

BottleneckDiagnosticTechniques, in order
Bytes moved (memory-bound)element-wise, norms, reductions; ceiling = bytes / ~900 GB/s1. fuse the op chain · 2. coalesce + vectorize (float4) · 3. shared-memory staging with bank-conflict padding · 4. __ldg / read-only path · 5. warp-shuffle reductions
Math throughput (compute-bound)large GEMM/conv; ceiling = tensor-core TFLOPS1. tiled matmul in shared memory · 2. mma.sync / TF32 or fp16 tensor cores, fp32 accumulate · 3. cp.async K-tile pipelining · 4. occupancy repair (--ptxas-options=-v) · 5. or: stay on cuBLAS and fuse the epilogue instead
Launch overhead (tiny kernels)runtime ≈ 2-5 µs per launchmerge kernels · precompute in __init__ · CUDA graphs only for static sequences
The stop rule

Iterate one technique per edit, re-verify, re-benchmark. Stop at 10-20% from the roofline, or after three consecutive attempts gain under 2% (the noise floor). This rule exists because the throttling makes endless micro-tuning a trap.

Roofline, this machine

The skill quotes ~900 GB/s GDDR7 as the spec ceiling. The skill-condition agent later measured 540 GB/s achievable linear read under the throttle; the skill's numbers are spec sheets; the pilot's numbers are the machine (slide 10).

The protocol · 06

A/B: one model, two conditions, one serial evaluator

Both conditions are the same base model instantiated as subagents of the same thread; nothing differs except access to the skill

  KernelBench problem (reference Model + get_inputs + fixed shapes)
        │
        ├──▶ Condition NOSKILL: plain task prompt
        │         └─▶ agent run ──▶ pilot/<problem>/noskill/model_new.py
        │                                    │
        └──▶ Condition SKILL: same prompt          │
              + "read and follow                  │
               cuda-kernel-super first"           │
                    └─▶ agent run ──▶ pilot/<problem>/skill/model_new.py
                                                    │
                                                    ▼
              ┌────────────────────────────────────────────────────────┐
              │ SINGLE SERIAL EVALUATOR (bench.py, one scoring session)│
              │  1. two-seed correctness, allclose(1e-2, 1e-2)         │
              │  2. L2 cache flushed (256 MB zero_) between reps       │
              │  3. ref and candidate INTERLEAVED, medians of 100 reps │
              └────────────────────────────────────────────────────────┘
                                    │
                                    ▼
              speedup = ref_ms / cand_ms   (ratio only; slide 09 explains why
                                           absolute milliseconds do not travel)
Why one wave at a time

The two agents of a wave run in parallel but their self-timing shares the GPU; final scores are always produced serially afterward, never from an agent's own claim. Agent self-timings are recorded only as corroboration.

Anti-gaming

Two seeds with fresh inputs, a reward-hacking rule in both prompts ("no caching, no hard-coded outputs"), and an evaluator that reseeds before each model construction.

Protocol as executed 9-10 November 2026; every run's solution file and self-report are preserved under /home/danie/KernelBench/pilot/.

Results · 08

Correctness histogram: every scored kernel inside the gate

Max absolute deviation from the reference for each scoring run, on a log10 axis. The gate is allclose(rtol=1e-2, atol=1e-2); every bar left of 10⁰ passes with margin

Runs: softmax 2.7e-12 and 1.4e-12 (Triton/CUDA fp32 exact-path), sum reduction 0.0022 and 0.0044, matmul 0.055 (fp16 inputs) and 0.757 (TF32), GEMM+LeakyReLU 0.0011. Every pass has ≥ 3x margin; the fp16 matmul has ~180x margin against its per-element budget.
Reading the left edge

The two softmax kernels differ from the reference by ~10⁻¹²: bit-level agreement on a numerically hard op, because both reimplemented the same online-softmax rescaling in fp32.

Reading the middle

The 10⁻²-to-10⁻¹ bars are tensor-core runs: TF32 and fp16 input rounding. Legal, they pass the gate, and the skill's tolerance-margin analysis (diff 0.055 against a per-element budget of ~10) is exactly the reasoning that keeps them honest.

Verified, not claimed

Every scored run was verified on two seeds with fresh inputs; no solution caches outputs or hard-codes results. The gate plus fresh inputs is what makes the speedup numbers on the previous slide trustworthy.

Values from bench.py max_abs_diff fields, one scoring session, 10 Nov 2026.
Measurement reality · 09

Trend chart: the same reference kernel, three sessions, a 12x swing

Median time of the identical softmax reference across scoring sessions. Absolute milliseconds do not survive this machine; ratios do. This is why the pilot's metric is the speedup ratio and nothing else

Median ms of torch.softmax on the identical problem, five scoring runs across two days, no kernel change between any of them. The 630-717 ms cluster predates the final measurement harness and was measured under 55 W throttling; 253 ms is the final harness; 55.9 ms was the agents' healthier-clock session. Same GPU, same kernel, 12.8x spread.
Methodological consequence

Speedup ratios from interleaved reps stayed in a narrow band across all of this (0.80-1.25x on softmax across sessions); raw milliseconds moved 12x. Cross-session comparisons of absolute time on this machine are meaningless, and any benchmark protocol that does not control for it produces fiction.

Data from the scoring log; timestamps are WSL2 local time.
Roofline · 10

Bandwidth reality: why both agents tied torch on the memory-bound problems

The skill-condition agent measured the machine before optimizing: pure linear read bandwidth under throttle. That single number explains the softmax and sum-reduction results

Roofline arithmetic from the skill agent's sum-reduction report: 8.59 GB input, isolated-kernel mins 15.3 ms (ref) vs 15.5 ms (kernel), both ≈ 530-540 GB/s.
What follows

When the ceiling is bandwidth and the reference already touches it, no kernel technique wins. The 0.79x-0.97x scores on memory-bound problems are not agent failures; they are the machine refusing to be beaten at parity. The skill's stop rule (three attempts under 2% → stop) prevented both agents from burning turns on an impossible target.

Where wins live

Compute-bound problems are a different story: torch's fp32 SGEMM leaves 2-3x on the table for any solution that may change input precision under the tolerance gate. That is where both conditions' only >1.4x results came from.

540 GB/s: skill agent measurement, 10 Nov 2026. Spec ~900 GB/s: RTX 5080 Laptop GDDR7 class. Achieved TFLOPS on matmul under throttle: ~12.4 (noskill agent measurement).
Verdict · 11

Measured answer: the skill buys peak speed where physics allows it

Same model, same problems, same evaluator. The difference the skill makes is not uniform; it is concentrated exactly where its guidance has something to say

Mean speedup, correct solutions
1.53×

skill condition (3 runs) vs 1.22x noskill (4 runs)

Fastest kernel of the pilot
3.69×

fp16 tensor-core GEMM with fused bias + scale + LeakyReLU epilogue

Largest scored effect
2.81×

fp16 tensor-core GEMM with fp32 accumulate: the skill's "don't hand-roll against cuBLAS; change precision under the tolerance gate; fuse the epilogue" path

Where the skill did NOT help

Memory-bound problems: both conditions scored 0.79-0.97x against references that already saturate the throttled 540 GB/s. The skill cannot repeal the roofline; it correctly told its agent to stop trying (the stop rule), which saved turns, not milliseconds.

What the pilot wrote back

Three rule changes shipped into the skill during the pilot itself: interleaved timing, profiling hygiene, and a robustness rule (slide 12). The next agent inherits them for free.

Verdict restricted to what was measured: 4 problems, 1 model, 1 GPU, 1 scoring harness. It is a pilot-sized experiment, not a leaderboard claim.
Closing the loop · 12

Skill v1.1: the pilot wrote back into the skill

A skill is only worth installing if the benchmark can change it. Three changes shipped while the pilot was still running

ChangeTriggerWhere it lives now
Interleaved timing rule: never time A fully before B; alternate reps, compare mediansSmoke test showed identical code at 0.65x; both wave-1 agents independently hit the same wallSKILL.md §Benchmark honestly + bench.py itself
Clone once, outside the clock; realistic-shape profilingSkill agent proved the timed region was 94% memcpy on 8.6 GB inputsbench.py + pitfall material
Pitfall #15: never manipulate global RNG state; report harness anomalies, never patch them in the solutionRobustness review of the fusion runreference/pitfalls.md
The pattern

Benchmark → failure → rule → skill. Each iteration is cheap (one pitfall, one paragraph), which is the same economy the ESL zero-program applies to MISRA fixes: versioned, reviewable units of improvement, not one-off patches.

Unchanged by design

The technique catalog needed no edits: every technique it recommends was either used by a winning run or correctly deprioritized by a stop rule. The catalog predicted the matmul result before the pilot ran it.

Bottom line
