01

The Two-Widenings Bug

MISCOMPILATION

MSVC /O2 miscompiles a short → unsigned int widening and reuses the wrong sign extension

The bug: res = (unsigned int)v4 where v4 is a short holding -1 must store 4294967295. Under MSVC v19.51 /O2 it stores -1.
Reported by: Ofek Shilon — Microsoft Developer Community, July 2026. More convoluted than bug #1 (3 nested loops), but still a reasonable compiler-bug repro. The repro is fragile and sensitive to register allocation.
Regression: v19.50 /O2 compiles it correctly. Only v19.51 (VS 18.6) /O2 is broken — and unlike bug #1, /O1 is NOT affected.

The Repro
02

One Store, Two Answers

#include <stdio.h>

int v0 = 1;   int v1 = 1;   int v2 = -84;
long long int v3 = -1;
short v4 = -1;
int b = 0;
long long int res = 1;

constexpr void test(int v0, int v1, int v2,
        long long int v3, short v4) {
  for (int i_0 = 0; i_0 < (int)(v3 >= v4); i_0 += 1) {
    for (int i_2 = 0; i_2 < v1; i_2 += 1) {
      printf("x");
      if (v2 < (unsigned int)(v1 ? -2 : -1)) {
        for (int i_4 = 1; i_4 < 2; i_4 += (v4 ? v0 : 1))
          b = v1 && v0;
      }
    }
    res = (unsigned int)v4;   // ← the victim
  }
}

int main() {
  test(v0, v1, v2, v3, v4);
  printf("%lld\n", res);
}
x64 msvc v19.51 — /Od (and GCC, Clang at any level)x4294967295 ✅
x64 msvc v19.51 — /O2x-1 ❌
The semantics: (unsigned int)v4 = (unsigned int)(-1) = 0xFFFFFFFF = 4 294 967 295. Converting that to long long is value-preserving: res must be 4294967295.
No UB escape hatch: the function is constexpr-callable — the whole program is UB-free, so the compiler has no license to do this.
Root Cause
03

v4 Must Be Widened Two Different Ways

Same 16-bit source value — two different 64-bit results

Use in sourceConversion chain64-bit value for v4 = -1
v3 >= v4short → long long (sign-extend all the way)0xFFFFFFFFFFFFFFFF (−1)
res = (unsigned int)v4short → int (sign-extend) → unsigned int (reinterpret) → long long (zero-extend)0x00000000FFFFFFFF (4294967295)
Claude's assembly-level diagnosis (quoted in the report): "The source needs v4 widened two different ways. MSVC /O2 computes only one and reuses it."
In x64 terms: use #1 needs movsx rax, v4 (sign-extend 16→64). Use #2 needs movsx eax, v4 (sign-extend 16→32; writing a 32-bit register zero-extends the upper half for free). MSVC computed the first and reused it for the second.
Root Cause — The Assembly
04

Right Value Computed, Then Thrown Away

MSVC v19.51 /O2, main with test inlined — verified via the Compiler Explorer API

; v4 sign-extended to 64 bits — for v3 >= v4
movsx   rbp, WORD PTR v4      ; rbp = 0xFFFF…FFFF
cmp     QWORD PTR v3, rbp     ; -1 >= -1 ✓
…
; correct value for res prepared BEFORE the loop:
mov     eax, ebp              ; rax = 0x00000000FFFFFFFF ✅
…
$LL9@main:                     ; inner loop body
call    printf                 ; ← rax clobbered!
…
mov     eax, 1                ; ← rax reused as counter
…
; after the loop, rax re-materialized:
mov     rax, rbp              ; rax = 0xFFFF…FFFF ❌ WRONG
$LN8@main:
mov     QWORD PTR res, rax    ; res = -1
Step 1 — correct: before the loop, mov eax, ebp builds the zero-extended value 0x00000000FFFFFFFF in rax. This is exactly what res needs.
Step 2 — the clobber: the inner loop uses rax for the printf call and as the i_4 loop counter. The prepared value doesn't survive.
Step 3 — the bug: after the loop MSVC re-materializes rax from the 64-bit sign-extended copy: mov rax, rbp — reusing widening #1 where widening #2 is required. res gets −1.
The fix is one letter: mov eax, ebp instead of mov rax, rbp. The rematerialization logic treats the two widenings of v4 as the same value — they are not.
Workarounds
05

The Fix That Doesn't Work

FAILED ❌

Same lesson as bug #1: intermediate variables and casts cannot beat value tracking

// Attempted fix: force the conversion through a separate unsigned variable
unsigned int tmp = (unsigned int)v4;
res = tmp;
Result: still prints x-1 under /O2 (verified on MSVC v19.51). The optimizer tracks tmp back to v4 and re-materializes it from the same wrong 64-bit register.
Pattern confirmed: in bug #1 the wrong range was tracked through every cast; here the wrong widened register is reused through every intermediate variable. Source-level laundering does not survive the optimizer — you must break its value tracking, not re-express the value.
Cast fix failed ❌ — z/qE1dYjc6z
Workarounds
06

The Fix That Works — volatile

WORKS ✅

A forced memory round-trip severs the link to the wrongly-widened register

// Fix: volatile forces a real store + reload — the optimizer
// can no longer re-materialize res from the sign-extended copy of v4
volatile unsigned int tmp = (unsigned int)v4;
res = tmp;
Result: prints x4294967295 under /O2 (verified on MSVC v19.51). The value written to tmp must be a genuine 32-bit unsigned int in memory, and the reload zero-extends it correctly.
Why it works: volatile makes the store and load observable side effects. The optimizer cannot substitute its register copy of v4 for the reload — the one substitution that was producing the wrong value.
volatile fix works ✅ — z/rMedMTsxx

The Fix That Works — #pragma optimize

WORKS ✅

Disable optimization for the affected function only — pragma goes OUTSIDE the function

#pragma optimize("", off)
void test(int v0, int v1, int v2, long long int v3, short v4) {
    /* … unchanged … */
}
#pragma optimize("", on)
Result: prints x4294967295 under /O2 (verified on MSVC v19.51). The whole function compiles as if /Od, so the bogus rematerialization never happens.
Two more flag-level escapes: compile the affected file with /O1 (not affected by this bug — unlike bug #1!) or pin the toolset to v19.50, which compiles the original code correctly at /O2.
volatileOne extra store/load. Most surgical — keeps /O2 for everything else.
#pragma optimizeDeoptimizes one function. Most reliable — immune to this whole bug class.
pragma fix works ✅ — z/4dvdKvKc8

Bug #1 vs Bug #2 — Same Species

#1 — Euclidean Remainder Fallacy#2 — Two-Widenings Bug
Wrong assumption% range is Euclidean [0, d−1]one widening of a short fits all uses

The common thread: both bugs live in MSVC's value-tracking machinery — a wrong fact about a value (its range, its widened form) is derived once and then confidently propagated everywhere. Source-level re-expression can't fix it; only breaking the tracking (volatile) or disabling the pass (#pragma, /Od) can.
