Wazatator
the spectator for your skills

Wazatator watches Claude Code use your SKILL.md: every prompt, tool call, and file. Then it scores the run, so you know whether a skill edit helped instead of guessing.

Presented by ESL (Engineering Software Lab), an Anthropic partner.

Open source · MIT Windows · macOS · Linux Claude Code plugin v0.1.0
The problem

You edit a SKILL.md with no proof the edit helped

Silent

Does the skill even fire?

Claude might answer from general knowledge and never invoke your skill. Nothing tells you.

Fragile

Vague prompts break it

"Explain this code" with no snippet: does the skill look for the file, or ask the user to paste it?

Unmeasured

Was v2 better than v1?

Without repeatable tasks and graders, every change is a vibe check.

What it is

A test runner for Agent Skills, driven by real Claude Code sessions

Like a spectator at a match

SpectatorWazatator
Watches the gameWatches the full Claude run: transcript, tools, files

Never playsDoesn't change your skill; it measures it

What's inside

CLI: wazatator, a fork of Microsoft Waza (MIT) with a new Claude Code executor.

Plugin: /wazatator:new-eval, /wazatator:eval, /wazatator:quality inside Claude Code.

Graders: text, regex, files, tool calls, skill invocation, token budget, trigger precision, and LLM-as-judge.

Output: results.json, a terminal report, model comparison, and a CI exit code.

How it works

From eval.yaml to a score in five steps

1WorkspaceFresh temp folder per task with your fixture files
›
2Install skillCopies SKILL.md to .claude/skills/ so Claude discovers it natively
›
3Run Claudeclaude -p --output-format stream-json with personal plugins and MCP turned off
›
4RecordMessages, tool calls, skill invocations, files, tokens, cost
›
5GradeRules plus an LLM judge that resumes the same session
internal/execution/claude.go (the core of the Claude Code executor)
args := []string{"-p", "--output-format", "stream-json", "--verbose",
    "--permission-mode", "bypassPermissions",
    // results depend on the skill under test, not on this machine's setup
    "--setting-sources", "project,local", "--strict-mcp-config"}
if req.SessionID != "" { args = append(args, "--resume", req.SessionID) } // follow-ups and judges
if len(req.Tools) > 0 { bridge, _ := startClaudeToolBridge(req.Tools) } // judge tools over local MCP
Code sample 1

An eval suite is one small YAML file

evals/code-explainer/eval.yaml
name: code-explainer-eval
skill: code-explainer
config:
  executor: claude-cli        # run through Claude Code
  model: sonnet
  trials_per_task: 3        # repeat to catch flakiness
  timeout_seconds: 300
  inject_skill_body: false  # Claude must find the skill itself
graders:                  # apply to every task
  - type: text
    name: no_errors
    config:
      regex_not_match: ["(?i)fatal error|crashed"]
tasks:
  - "tasks/*.yaml"

Why these settings matter

executor: claude-cli: real Claude Code sessions, the same way your users run the skill.

trials_per_task: models vary from run to run. Three trials show whether a pass is reliable.

inject_skill_body: false: tests real discovery. If the skill's description is weak, Claude won't pick it, and the eval shows that.

Exit codes: 0 = pass, 1 = test failure, 2 = config error, ready for CI.

Code sample 2

A task: a prompt, input files, and graders

tasks/explain-recursion.yaml
id: explain-python-recursion-001
inputs:
  prompt: "Explain this code to me"   # deliberately vague
  files:
    - path: factorial.py
expected:
  output_contains: ["recursive", "factorial"]
graders:
  - name: used-skill
    type: skill_invocation
    config:
      required_skills: [code-explainer]
      mode: any_order
  - name: judge
    type: prompt                    # LLM-as-judge
    config:
      model: haiku
      continue_session: true      # judge reads the real conversation
      prompt: |-
        If the answer explains the recursion and base case,
        call set_waza_grade_pass, otherwise set_waza_grade_fail.

Three layers of checking

Rules
output_contains, regex, JSON schema, file contents and diffs: fast, free and deterministic.

Behavior
skill_invocation, tool-call sequences, token and turn budgets: did Claude do the right things?

Judgment
prompt graders: a second Claude session reviews quality that keywords can't capture, and gives its reason.

Code sample 3

Trigger tests: does the skill fire only when it should?

trigger_tests.yaml
skill: pirate-greeter
should_trigger_prompts:
  - prompt: "Hello!"
  - prompt: "Say hello to my team"
  - prompt: "Good morning, how about a greeting?"
should_not_trigger_prompts:   # near-misses
  - prompt: "Translate this paragraph into Spanish"
  - prompt: "Tell me a pirate joke about coffee"
  - prompt: "Proofread this email for typos"

Precision catches a skill that grabs requests it shouldn't (the pirate joke). Recall catches a skill Claude never picks. Each trigger run stops as soon as the skill fires, which saves tokens.

What it can find

Real findings from real runs

Skill weakness

Asks instead of acting

"Explain this code to me" got "I don't see any code in your message yet", even though factorial.py was right there.

Skill weakness

Ignores the input file

Judge: "fails to greet Priya… asks for clarification about who the person is." The name was in newcomer.txt.

Discovery

Skill never invoked

Trigger recall 0%: with the skill pasted into the prompt, Claude answered without ever calling its Skill tool.

Safety

Tool-policy violations

A read-only agent (tools: ["read"]) was asked to write a file. Only Read was available; any other call fails the run.

Integration

MCP tool usage

Mocked GitHub MCP server: Claude called mcp__github__list_issues and reported issue #363. Wrong arguments fail loudly.

Cost

Tokens and dollars

5 tasks + judges + 9 trigger prompts: 72 s, 2,685 output tokens, about $0.31 on Sonnet.

Finding → fix → proof

"I don't see any code": fixed in the skill, proven by a re-run

code-explainer/SKILL.md (the fix)
+ ## Finding the Code
+ If the user refers to "this code" but no snippet is in
+ the message, do not ask for the code right away:
+ 1. Use code from the conversation or attached files.
+ 2. Otherwise list the working directory. If there is
+    exactly one source file, read and explain it, and
+    say which file you explained.
+ 3. Ask only when there is no candidate or several
+    equally likely ones.
TaskBeforeAfter (3 trials)
"Explain this code to me"✗ asked for code✓ 3/3
"Explain the code in factorial.py"✓✓ 3/3
tools: Skill → Glob → Glob → Read
output: "I explained `factorial.py`, since it's the only
        source file in the working directory. ..."

The fix went into the skill, not the test, so real users benefit too.

Inside Claude Code

The plugin: ask Claude to test your skill

Three slash commands

/wazatator:new-eval pirate-greeter
  # writes eval.yaml, 5 tasks, fixtures, trigger tests

/wazatator:eval evals/pirate-greeter/eval.yaml
  # runs it, explains failures, proposes SKILL.md fixes,
  # re-runs and compares old vs new results

/wazatator:quality skills/code-explainer
  # static check + LLM review of the SKILL.md itself

Tested live: Claude Code ran the plugin, which ran Wazatator, which ran its own Claude Code sessions.

Get started

Install in two commands

1. CLI (Windows PowerShell)
irm https://raw.githubusercontent.com/zuwasi/wazatator/main/install.ps1 | iex
1. CLI (macOS / Linux)
curl -fsSL https://raw.githubusercontent.com/zuwasi/wazatator/main/install.sh | bash
2. Plugin (inside Claude Code)
/plugin marketplace add zuwasi/wazatator
/plugin install wazatator@wazatator

Requirements

Claude Code installed and logged in. Every task and judge is a real session on your account, so keep trials_per_task: 1 while iterating.

Also works with

MCP servers and hermetic MCP mocks, .agent.md tool policies, follow-up turns, reasoning effort, CI gating, and side-by-side model comparison with wazatator compare.
