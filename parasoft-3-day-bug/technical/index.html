The story · 02

Three days. One line of C++. A bug that only crashed in Release

Jawwad Akhter's post (LinkedIn, 23 November 2026), compressed to its bones

What happened
  • Debug build: ran it a hundred times, nothing
  • Release build: crashed about once in 20 runs
  • Attaching a debugger made it stop crashing
  • Crash dump in WinDbg: a normal-looking if on a member, with a value that made no sense
  • Root cause: one constructor initialized the member, a later one did not. The fix was bool m_ready = false;
The advice the post gave
  • Initialize variables where you declare them
  • Enable compiler warnings (-Wall -Wextra, /W4)
  • Use MemorySanitizer, AddressSanitizer, ThreadSanitizer or Valgrind where applicable
  • Get a crash dump instead of trusting breakpoints
All good advice for finding the next bug faster. The question we tested: could a static analyzer have flagged this bug before it ever shipped, in seconds, with none of that debugging craft?
The repro · 03

We rebuilt the bug exactly as told: one missing = false

session.cpp, 54 lines: two constructors, one forgotten member, and a crash path behind it

class Session { explicit Session(int id) : m_id(id), m_ready(false), m_stream(nullptr) {} // original, correct explicit Session(const char* name) : m_id(0) {} // added later: m_ready forgotten bool start() { if (m_ready) { return send(); } return false; } // the crash-dump if-check bool send() { m_stream[0] = 'S'; return true; } // writes through the stream ptr int m_id; bool m_ready; char* m_stream; };
2 / 20
Release runs crashed (0xC0000005) on the forgotten-constructor path, after dirtying one heap block the way any real process would
0 / 20
Release runs on the correct-constructor path: never crashed, exit code 1 as designed
9 / 30
Debug build also crashed on the same path here: Debug vs Release is memory layout, not safety
Measured 23 November 2026, cl 14.51.36231 /O2 and /RTC1 builds of session.cpp; 20 to 30 automated runs per configuration, exit code 0xC0000005 counted as a crash
The scan · 04

One CLI command. No test runs, no debugger, no crash dump

The findings · 05

Both findings point at the exact line from the crash dump

The same conclusion the author reached after 3 days of WinDbg, delivered as review comments

What each finding says

INT-06 · line 11

"Constructor does not initialize members: 'm_ready, m_stream'"

Fired on the constructor the post says was "added later by someone in a hurry". The one-line fix, handed over as a review comment.

BD-PB-NOTINIT · line 14

"Non-initialized "this->m_ready" is used"

Flow analysis traces the whole path: Session* s → condition argc > 1 (assuming true) → new Session("edge-device") → the if (m_ready) read, and marks the constructor as the source of the uninitialized value.

The honest compiler test · 06

The post's advice would not have caught it

We ran every compiler check the post recommended on the same file. Here is what each one reported

CheckWhat it reported on session.cppBug caught?
cl /W4 (the post's advice)C4100 unreferenced parameter onlyno
cl /W4 /analyze (default rules)C4100 only, no C6xxx or C26xxx findingno
/analyze + Core Guidelines checker (AllRules + EspXEngine)C26495 on both constructors: "Variable 'Session::m_ready' is uninitialized"yes
Parasoft Recommended RulesINIT-06 + BD-PB-NOTINIT with the traced crash path, MISRA/CERT mapping includedyes
Fair to the compiler: it can catch this bug, but only after you enable the right checker engine and keep it on in CI. Fair to the sanitizers: AddressSanitizer and MemorySanitizer catch runtime-only bugs static analysis cannot see. They are complements, not competitors.
The cost · 07

3 days of senior debugging vs 15 seconds in the pipeline

And the intermittent crash means those 3 days are the optimistic case: some field bugs are never explained at all

3 days
One senior engineer, one lucky crash dump, one reproducible-enough crash. Plus the risk it ships to customers first
15 s
Static analysis on one file in the pipeline. Whole-project scans still finish in minutes, once, on every commit
0
Test runs, debug sessions, or luck required. The finding arrives before merge, with the fix already written in its repair suggestion
This bug class is exactly what flow-analysis rules (BD-PB-NOTINIT) and initialization rules (INT-06) exist for: an indeterminate value read, where the same code works a hundred times in Debug and explodes once in Release.
