Step 1 / License preflight

Check the license.
Before scanning a project.

cpptest-license-features queries the license configured for a specific C/C++test CLI. No project analysis is performed.

The utility

Know what is available

  • Reports the CLI version and license mode
  • Distinguishes Automation, Desktop CLI, both or neither
  • Lists licensed, not licensed and unrecognized features
  • Text output for review; --json for saved evidence
The decision

Check before the long scan

  • For this demo: Automation, Static Analysis and Flow Analysis
  • For later workloads: check needed MISRA / CERT rule features
  • Resolve missing features or query errors before proceeding
  • Then verify actual execution with the nine-scan test project

A preflight check, not a capacity test. The utility does not prove three available server allocations or nine simultaneous analyses. Use the same container image and approved license settings as the scans.

Step 1 / Run and interpret the utility

Query the lab installation.
Review the feature list.

ESL supplies the utility separately. Run it in each target container environment before the verification scans.

# Set these paths for the actual installation and approved settings
./cpptest-license-features "$CPPTEST_PROBE_CLI" \
  --settings "$CPPTEST_SETTINGS" --json > license-features.json
Features

Confirm the required features are present. Exit 0 means the query succeeded, not that every required feature is licensed.

Not licensed / errors

Resolve required features marked Not licensed. Exit 2 means a query failure, such as license access, timeout or an unexpected response.

Not recognized

The CLI does not expose that feature name through this check. Treat it as inconclusive, not proof that the feature is unlicensed.

Compatibility gate: uses undocumented -check-license, verified on Windows 2025.1 and Linux 2025.2, not Xsight's 2023.1.1 image. Linux 2025.2 needs cpptest/bin/cli/cpptestcli, not its top-level launcher. Confirm the probe path/support with Parasoft for the lab version; keep the existing scan command unchanged.

Step 2 / Verify with the test project

Same workload.
More scans at once.

After license preflight, use the nine-app project to verify the move from one scan per container to three independent scan processes.

3 concurrent scans · 3 waves per container

Scheduling illustration only. Both modes produce nine reports in total. This is a concurrency target, not a measured 3× speedup. The baseline switch limits scheduling; it does not change the installed license edition.

The runner builds and analyzes these programs; it never executes their defective paths. These are intended defects, not promised detection counts. Findings depend on the scanner version and enabled rules.

Step 2 / Execute the verification

Prepare. Launch. Observe.

After reviewing the utility's feature list, run the test project on the Xsight lab server in a reserved test window.

PREPARE

Connect the lab

Set the image in .env, mount the same approved settings used for preflight and build the demo image.

LAUNCH

Start all three workers

All nine sample builds finish before scanning starts. Each worker then launches three scan processes.

OBSERVE

Collect evidence

Inspect container processes, resource usage and License Server token details while the scans are active.

# Optional baseline: one scan at a time in each container
python3 lab.py run --mode standard

# Automation target: three scans at a time in each container
python3 lab.py run --mode automation

Tiny-sample defaults: 3 CPUs and 10 GiB limit per container, 2 GiB Java heap per scan. Reserve additional host/native-engine headroom. These are starting values, not production sizing.

Verification / Acceptance criteria

Prove execution.
Confirm the granted licenses.

The utility checks available features first. The test project and live License Server evidence verify the three-by-three configuration.

Automated technical checks

Did the workload run correctly?

  • Three distinct container hostnames
  • Nine completed native XML reports with findings
  • Positive common overlap of all nine CLI processes
  • No licensing, setup or timeout failures
License Server evidence

Were the right features granted?

  • Three concurrent machine/container allocations
  • Granted Automation and required analysis features
  • Analysis-phase logs matched to active processes
  • Administrator confirmation of entitlement coverage

Process overlap alone is not proof of licensed engine overlap. Capture token details while the jobs are active. A requested feature list does not establish what the License Server granted.
