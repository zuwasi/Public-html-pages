Why this exists

The graph was git-only. The code isn't.

What Auryn does

  • Ingests a repo or directory into a FalkorDB code graph: functions, calls, types, modules, imports.
  • Coding agents query it over MCP: "who calls this?", "what breaks if I change it?", blast radius, impact.
  • Keeps the graph fresh on commit / save, incrementally.

What was missing

  • Commercial and regulated code often lives in Helix Core (Perforce), not git.
  • Depot paths //depot/proj are not checkouts, so the git and directory sources don't apply.
  • Result: agents fly blind on exactly the projects where structure matters most.

The question that started this: "can we fit it to Perforce projects?" — answer: yes, as a new Source plugged into the existing machinery, not a fork of the pipeline.

The core piece

P4Source: a Source that reads the depot, not a checkout

It implements the same small interface every backend already speaks — list_files, read_blob, tree_sha, diff_changed_files — so parsers, filters, hooks, and sync all work unchanged.

p4 fstat -Ocdfile list with per-revision MD5 digests, exactly as of one submitted changelist
→
p4 print -qfile contents streamed from the depot on demand — no workspace sync
→
Pinned snapshot//depot/proj@48213 is a reproducible tree; head = @now
  • One changelist is one tree: the CL number plays the role git's commit sha plays — same dedup, same delta logic, same "graph state = source state" guarantee.
  • Connection via P4Settings: -p / -c / -u built from explicit flags; passwords never go on the command line (ticket auth via P4PASSWD in the environment).
  • Nothing silently empty: an unmatched depot path raises a clean error instead of ingesting zero files.

Step 2 · Keep fresh

Sync: re-parse only what a submit touched

auryn sync //depot/proj
Re-resolve head CLregistration stores depot path + P4PORT / P4CLIENT / P4USER
→
Diff digestsfstat at head vs fstat at the ingested CL
→
Delta ingestonly changed files are re-parsed; blast radius stays intact
  • The ingested CL is stored on the project, so the next sync knows exactly what it last saw — the same contract as a git sha.
  • Respects the same lock as every other sync path: overlapping syncs of one project queue instead of corrupting the subgraph.
  • Manual sync always works — the triggers below only decide when it runs.
Step 3 · Automation

Three ways the graph stays current

ModeHow it firesWho it fits
manualYou (or CI) run auryn sync //depot/proj when you want it.Controlled environments, batch schedules.
submit · pollerauryn p4-watch polls p4 changes -m1 per registered depot path every 30 s (AURYN_P4_POLL_SECONDS) and spawns a sync on advance. One cheap command per depot per tick, non-overlapping.Most users — no p4d admin rights needed; runs on your machine.
server triggerA real p4d change-commit trigger form invokes auryn sync //depot/proj on the server host.You administer p4d — true event-driven freshness.

Why a poller at all? p4d executes triggers on the server's host, which is usually not the machine running Auryn. The poller is the local, permission-free equivalent of the trigger — same command, same code path.

auryn ingest p4 //depot/proj --port perforce:1666 --user you --client ws --trigger submit # registers + starts the poller

Why this matters for a P4 shop

Benefits: the depot side

Depot-direct

Ingest a project you never checked out: revisions stream from the server. No workspace reservation, no disk-heavy sync of huge depots.

Changelist-pinned reproducibility

Every graph is a snapshot of one submitted CL — the same property that makes Perforce attractive for audited, safety-critical work is inherited by the graph.

Cheap freshness

Incremental sync re-parses only files whose fstat digest changed between CLs. A one-file submit costs one file, not one depot.

Nothing new to run

Uses the p4 CLI and the Perforce auth you already have, plus a FalkorDB container. No server-side agent, no daemon inside the depot, no license.

Why this matters for agents

Benefits: the agent side

Structure on demand

Call graphs, definitions, and impact analysis answered in milliseconds from the graph instead of whole-repo greps inside a slow workspace.

One graph, many sources

P4 depots sit next to git repos, directories, SQL/Oracle schemas in the same workspace — cross-source questions become one query.

Same upstream machinery

Filters, post-ingestion hooks, deep semantic passes, auryn mcp — everything the git path has, the p4 path inherits for free.

Offline querying

Once ingested, the graph is local: agents answer structural questions with no Perforce connection, no internet, no server round-trips.

Test drive

How to test it on your own project

  1. Prerequisites: p4 CLI on PATH, Python 3.12 venv from the repo, FalkorDB reachable (Docker: docker run -p 6379:6379 falkordb/falkordb), and p4 login done if your server needs a ticket.
  2. Ingest from your Helix server:
    auryn ingest p4 //yourdepot/yourproj --port yourserver:1666 --user you --client ws --trigger submit
    No need to sync a workspace first — depot-direct.
  3. Query it: auryn mcp (or auryn list, auryn stats) and ask your agent "who calls function X in this project?"
  4. Submit a change: edit a file in any workspace, p4 submit. Within ~30 s the poller syncs the delta; check with auryn list (tree hash changes) or a fresh agent query.
  5. Control the poller: auryn p4-watch --status / --stop / --foreground. All state lives under ~/.auryn; auryn forget //your/depot/yourproj removes the project.
Honest edges

Offline behavior and prototype limits

Works offline

  • Querying the graph (MCP tools, auryn list, Cypher): fully offline — the graph lives in your local FalkorDB.
  • Embeddings run locally (fastembed); the model downloads once, then no network.

Needs the server

  • Ingest & sync read live depot revisions; the prototype keeps no local depot cache, so a fresh sync offline is not possible yet (a cached-tree mode is a natural next step).
  • On Windows, use Docker/local FalkorDB — the embedded server is POSIX-only.

Prototype limits

  • Submitted changelists only — no pending or shelved CLs.
  • Auth via p4's environment / ticket (P4PASSWD); no per-file integration/merge complexities modeled.

Next steps
