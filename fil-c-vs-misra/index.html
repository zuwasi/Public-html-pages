Fil-C vs MISRA C:
a measured challenge to the
memory-safety claims

A LinkedIn post presents Fil-C as a compiler swap that makes existing C/C++ memory safe. We did not argue with it. We measured it: the same bug suite and benchmarks run seven ways on the same machine, including safe Rust, unsafe Rust, Zig, and the compiler's own assembly.

Summary of the post | five claims

Five claims worth challenging

1
Makes existing C/C++ memory safe, without rewritingFil-C as a drop-in compiler swap for unmodified sources
2
Covers buffer overflow, use-after-free, double free, bad pointer dereferenceThe exact bug shapes the post names
3
No mechanism to turn the checks offUnlike Rust, per the post
4
The price is only "higher memory and lower performance"The post's entire cost model
5
Changing the compiler is cheaper than rewriting to RustThe post's recommendation

What the post never mentions: Fil-C only checks code paths that actually execute, at runtime, in production. Static analysis checks all of them, at build time. We measured both.

Method | seven treatments

What we did

Agcc -O2, the status quo. What happens to each bug on a normal production toolchain today.
BFil-C 0.687, Pizlo's clang 20.1.8 fork with InvisiCaps and a concurrent GC. Compiled with -O2, zero source changes.
CParasoft MISRA C 2025, static analysis with the built-in MISRA C 2025 configuration, including flow analysis. Zero runtime cost by design.
DSafe Rust, rustc 1.97.1 -O. Ownership plus bounds checks: the same bugs, direct ports, byte-identical benchmark output.
EUnsafe Rust, raw pointers, the way you touch hardware from Rust. The language's escape hatch, measured honestly.
FZig 0.17.1 ReleaseSafe. Bounds checks plus a safety allocator: language-level safety with explicit allocators.
GESL Assemblomator on the compiler's own x86-64 assembly: what a static analyzer can still see after the C is lowered away.

Bug suite: 5 standalone programs, one violation each. Benchmarks: 3 clean programs with different pointer intensity (float-heavy, array-heavy, allocation-heavy). Same machine, same sources, same flags.

Exhibit T-1 | the tool

What is Parasoft C/C++test?

Commercial static analysis and test suite for C and C++ by Parasoft, standard equipment in avionics, automotive and medical device development
Flow analysis: simulates execution paths at build time to find out-of-bounds access, use-after-free, double free and uninitialized use without running the code
Coding-standard rule packs: MISRA C and C++, AUTOSAR, CERT, CWE, OWASP, plus compliance reporting
Also does unit testing, code coverage and on-target test execution for embedded toolchains
Editions: Standard (command-line static analysis) and Professional (IDE, CI, unit tests). This benchmark used Standard 2026.1.3 via cpptestcli in WSL
Why it is in this comparison: it is the build-time alternative to Fil-C's runtime checks, and the tool most regulated C shops already run
Exhibit S-1 | the standard

What is MISRA C 2025 / MISRA C++ 2023?

22Mandatory guidelines, MISRA C:2025
151Required guidelines
45Advisory guidelines
219Guidelines total, plus directives
MISRA (Motor Industry Software Reliability Association) publishes coding guidelines for writing C and C++ that is safely analyzable: MISRA C 1998 → 2004 → 2012 → 2023 → 2025, and MISRA C++ 2008 → 2023
Structure: guidelines classified Mandatory / Required / Advisory; deviations are possible but must be documented and justified, which is how compliance is audited
MISRA is a document, not a tool: enforcement happens with static analysis engines that ship the rules built in, like the Parasoft configuration used here
In this benchmark the MISRA C 2025 config caught all 5 bugs at build time, and Dir 4.12 / Rule 21.3 go further: they flag dynamic heap allocation itself, removing the whole bug class instead of catching it

Exhibit R-2 | the granule boundary

The off-by-one overflow is not caught

Write offset past an 8–10 byte allocationFil-C
+1 to +7 (offsets 8–15)allowed, exit 0
+8 (offset 16)filc panic
+9 to +992 (offsets 17, 100, 1000)filc panic
1
Same result everywhereOn the heap (malloc(10)) and the stack (char a[8]), at both -O0 and -O2.
2
InvisiCaps track the allocator's 16-byte granule, not the requested sizeA one-past-the-end write, the most common overflow shape in real CVEs, lands in allocator padding and runs silently. Not a soundness hole in Fil-C's own model, since the write cannot corrupt other objects, but the accurate claim is "cannot touch other objects", not "covers buffer overflow".
probe_heap.c · filc-0.687 · -O2
#include <stdio.h>
#include <stdlib.h>
int main(int argc, char **argv) {
    int off = atoi(argv[1]);
    char *buf = malloc(10);  // Fil-C granule: 16 B
    buf[off] = 'X';  // ← the write under test
    printf("heap wrote buf[%d]: OK\n", off);
    return 0; }
$ ./probe_heap 15  heap wrote buf[15]: OK · silent, exit 0

!
WhyIn Fil-C, free() does not return memory to the OS. It invalidates the capability; collection happens later, in concurrent GC cycles. Every production process now runs a garbage collector. Rust and Zig stay at C-level memory on the same benchmark.

MISRA goes one step further: Dir 4.12 and Rule 21.3 flag dynamic heap allocation itself on every file. In ISO 26262 / DO-178C / IEC 61508 domains the prescribed answer is to remove the bug class, not to contain it at runtime, and a GC plus 4× slowdown is usually disqualifying.

And Fil-C itself in this table: Linux x86_64/ARM64 userland only, no qualified toolchain, no published coding standard, cannot link with non-Fil-C objects (including Rust), and its runtime is written in unsafe code. In DO-178C / ISO 26262 programs an unqualified runtime plus a GC in every process is usually disqualifying, which is why MISRA-style static analysis remains the default gate.

Exhibit A-1 | the control group

What about assembly?

1
Lowering destroys the facts a source analyzer needsAfter gcc -S, every type, bound, and lifetime fact is gone: bug1 is address arithmetic and a call to malloc, bug3 and bug4 are two calls to free with nothing between them. Stock rules score 0/5
2
One bug class survives lowering, and one new rule catches itWe added ASM-X86-015 upstream: dereference of a register holding a hardcoded immediate address. It flags bug5's wild store at -O0 and -O2, quiet on the other nine files: 1/5 total
3
Not a comparison candidateCompiled assembly is the output of one of the languages, not a competing language choice. Its 1/5 measures how much information lowering destroys, not how safe assembly programmers are.
4
Where assembly analysis does belongCode authored in assembly: boot code, ISRs, crypto primitives, certified under DO-178C/ED-12C where the shipped artifact is the assembly. That is Assemblomator's day job; here it served as the control group.

Verdicts | claim by claim

Verdicts

1
"Memory safe without rewriting": mostly holdsAll 5 files compiled unchanged; but the guarantee is runtime-only
2
"Covers buffer overflow": overstatedOff-by-one writes inside the 16-byte granule run silently
3
"No way to turn checks off": trueBut the ABI cannot link with non-Fil-C objects, including Rust, and the runtime is itself unsafe
4
"Higher memory, lower performance": undersoldMeasured up to 5.4× slower and 27× peak memory, plus a GC in every process, Linux x86_64/ARM64 only
5
"Cheaper than rewriting": incompleteIt ignores that static analysis finds the same bugs at build time at zero runtime cost, and that safe Rust and Zig reject the entire suite outright (5/5 each) at a fraction of Fil-C's runtime price
Takeaways | what to do with this

Fil-C is a safety net, not a substitute for static analysis

Fil-C contains bugs that slip through: genuine value for legacy deployments
Static analysis prevents them from shipping at all, with zero runtime cost
The two are complements: Parasoft finds it before release, Fil-C contains it if it slips through
Escape hatches measured: unsafe Rust behaves like C (0/5), lowered assembly like assembly (1/5). Safety comes from what the tool can still see
