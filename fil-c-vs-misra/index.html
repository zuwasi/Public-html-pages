Fil-C vs MISRA C:
Challenging the Memory-Safety Claims

A LinkedIn post presents Fil-C as a compiler swap that makes existing C/C++ memory safe. We did not argue with it. We measured it: the same bug suite and benchmarks run three ways, on the same machine.

Fil-C 0.687gcc 13.3Parasoft C/C++test 2026.1.3 · MISRA C 2025

WSL2 Ubuntu 24.04 · 24 cores · all sources unchanged · November 2026

The post's claims

Five claims worth challenging

  • 1Fil-C makes existing C/C++ memory safe, without rewriting
  • 2It covers buffer overflow, use-after-free, double free, and bad pointer dereference
  • 3Unlike Rust, there is no mechanism to turn the checks off
  • 4The price is only "higher memory and lower performance"
  • 5Changing the compiler is cheaper than rewriting to Rust

What the post never mentions: Fil-C only checks code paths that actually execute, at runtime, in production. Static analysis checks all of them, at build time. We measured both.

The finding that challenges the post

The off-by-one overflow is not caught

Write offset past an 8–10 byte allocationFil-C
+1 to +7 (offsets 8–15)allowed, exit 0
+8 (offset 16)filc panic
+9 to +992 (offsets 17, 100, 1000)filc panic

Same result on the heap (malloc(10)) and the stack (char a[8]), at both -O0 and -O2.

InvisiCaps track the allocator's 16-byte granule, not the requested size. A one-past-the-end write, the most common overflow shape in real CVEs, lands in padding and runs silently.

This is not a soundness hole in Fil-C's own model: the write cannot corrupt other objects. But the post's categorical claim that Fil-C "covers buffer overflow" is not what a developer or an attacker experiences. The accurate claim is "cannot touch other objects".

Why: in Fil-C, free() does not return memory to the OS. It invalidates the capability; collection happens later, in concurrent GC cycles. Every production process now runs a garbage collector.

MISRA goes one step further: Dir 4.12 and Rule 21.3 flag dynamic heap allocation itself on every file. In ISO 26262 / DO-178C / IEC 61508 domains the prescribed answer is to remove the bug class, not to contain it at runtime, and a GC plus 4x slowdown is usually disqualifying.

Claim-by-claim

Verdicts

  • 1"Memory safe without rewriting": mostly holds all 5 files compiled unchanged; but the guarantee is runtime-only
  • 2"Covers buffer overflow": overstated off-by-one writes inside the 16-byte granule run silently
  • 3"No way to turn checks off": true but the ABI cannot link with non-Fil-C objects, including Rust, and the runtime is itself unsafe
  • 4"Higher memory, lower performance": undersold measured up to 5.4× slower and 27× peak memory, plus a GC in every process, Linux x86_64/ARM64 only
  • 5"Cheaper than rewriting": incomplete it ignores that static analysis finds the same bugs at build time at zero runtime cost
Takeaways

Fil-C is a safety net, not a substitute for static analysis

  • •Fil-C contains bugs that slip through: genuine value for legacy deployments
  • •Static analysis prevents them from shipping at all, with zero runtime cost
  • •The two are complements: Parasoft finds it before release, Fil-C contains it if it slips through
