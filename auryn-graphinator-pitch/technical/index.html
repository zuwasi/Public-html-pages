The problem · 02

AI agents answer code questions with text search, and text search cannot see the code structure

The most expensive questions in development, change impact, dead code, dependency paths, are exactly the ones grep answers badly, and the agent does not know it is wrong

Question typeWhat text search returnsWhat the question actually needs
Who calls this function?Files containing the string: definitions, imports, comments, calls, all mixedThe list of real call sites, direct and transitive
Change impact (2 hops deep)Thousands of matches, no path structure; agents extrapolate and miscountExact reachable set over the call graph
Dead code sweepCannot prove absence; misses calls hidden inside function-local imports and decoratorsEvery function with zero inbound call edges
Call path A to BNot answerable at all without reading every moduleThe actual chain of calls
Measured failure mode

Confident and wrong

On the meridian Perforce demo project, an agent working only from files enumerated the same pattern we did, summed its own enumeration incorrectly, and reported 126 functions that can reach the billing core. The verified answer is 185 (older seed) / 188 (current seed). Nothing in its output warned the reviewer.

The demo protocol · 04

Two agents, the same questions, one difference: access to the graph

The test project is a synthetic billing service (meridian) served from a real local Helix Core p4d server; every answer is graded against ground truth verified in the source, not against the graph's own opinion

Agent A

Files only

The agent sees the synced source files and has shell access for search and reads. This is how every coding assistant works today out of the box.

Agent B

Graph only

The same agent model, but its only tool is the code graph over MCP: Cypher, who_calls, find_path. It cannot read a single file.

Ground truth

Verified independently

Every answer cross-checked against the generated source structure: exact function counts, exact call chains, exact dead-code set including the tricky cases.

Honest limitation, measured

Dynamic dispatch is invisible to any static tool

Django passes callables around (get_response) and uses getattr, so request-path tracing from WSGIHandler.__call__ has gaps. Every static analysis tool has this ceiling. For Graphinator the pitch rests on exactness where the graph is complete, which the meridian and SBOMator slides demonstrate.

Reproduce · 12

Every number here is reproducible in under five minutes

The demo stack is one Docker container and one Python venv; the questions are single Cypher queries

# 1. FalkorDB in Docker
docker run -d --name falkordb -p 6379:6379 falkordb/falkordb:latest

# 2. Sync from Helix Core, then ingest the sync root
p4 -p 127.0.0.1:1777 -u tester sync //demo/meridian/... //ws/meridian
$env:PYTHONUTF8="1"; auryn ingest dir C:\ws\meridian --project-name meridian

# 3. Ask the reachability question (the one files-only agents get wrong)
MATCH (src:Function)-[:CALLS*1..6]->(t:Function)
WHERE t.id CONTAINS 'func.charge_card('
RETURN count(DISTINCT src)          -- answers in ~140 ms

# 4. Point any MCP-capable agent at the graph
python -m auryn mcp                 -- the agent now has who_calls, find_path, Cypher
