Factory DroidPart I · Requirements
Restricted
Requirements

Three sovereignties define the brief.

A government AI programme is unlike an enterprise one. It requires custody over data, model, and operation — not just preferential terms of service.

  1. Data sovereignty

    Source code must never leave the perimeter.

    Every character of your repository, every prompt, every tool call, every log line is a potential disclosure vector. The only safe posture is one in which no byte of source material ever crosses an outward boundary.

  2. Model sovereignty

    Weights must live on your silicon.

    A model you cannot inspect, pin, or re-run offline is not a sovereign asset. You must be able to freeze a known-good version and operate it indefinitely with zero vendor dependency, zero mandatory updates, and no runtime phone-home.

  3. Operational sovereignty

    No external control plane.

    A SaaS orchestrator that holds routing rules, approvals, or audit logs is a single point of foreign control. The agent, its policies, and its history must sit entirely inside your network — and remain functional even if the vendor ceases to exist.

Factory DroidPart I · Current state
Restricted
The Gap

Why current coding assistants cannot be used.

  • Cloud copilots. Every prompt, every file, every snippet is transmitted to a third-party API. There is no architectural option to disable this transmission — it is the product.
    rejected
  • "Enterprise" tiers. A no-training promise is not an air-gap. Traffic still crosses borders. Vendor outages still break the pipeline. Jurisdiction still applies to the host.
    rejected
  • Local model, hosted agent. Running a local LLM with a cloud-hosted orchestrator is the worst of both worlds: the agent phones home and cannot be audited.
    rejected

What the brief actually requires

  • Agent orchestrator inside the perimeter.
    yes
  • Model weights on local GPUs.
    yes
  • Configuration via local files only.
    yes
  • Telemetry to your own collector — or disabled entirely.
    yes
  • Verifiable: no path reaches the public internet.
    yes
  • Reproducible: same build, same output, offline, next year.
    yes

This is precisely the shape of Factory's air-gapped deployment.

The Boundary

What stays in. What never leaves.

Inside the perimeter

  • Source code, repositories, build artefacts
  • Model weights — quantised, pinned, versioned
  • Droid CLI binary and settings.json
  • Prompts, tool calls, agent plans
  • Audit logs and OpenTelemetry traces
  • Developer sessions and approval records
  • Pull-request history and code review
Air-Gap

Never crosses

  • Prompts to third-party APIs
  • Model output to vendor telemetry
  • Repository contents to a cloud agent
  • Credentials to Factory servers
  • Error reports containing code snippets
  • Analytics or usage "pings"
  • Runtime software updates

Factory DroidPart II · Installation
Restricted
Installation

Four steps to a working deployment.

  1. Hardware

    Rack the GPU server.

    Four H100 80 GB cards (SXM or PCIe) in a single node. NVLink helps tensor-parallel inference. Linux host, CUDA 12.4 or newer, Docker or bare-metal Python 3.11.

  2. Model weights

    Mirror the models.

    Download open-weight models on an internet-connected machine. Verify checksums. Transfer via approved media. Land under /models on the GPU host.

  3. Inference backend

    Serve the model.

    Launch vLLM for production or LM Studio for evaluation as an OpenAI-compatible endpoint on :8000/v1 or :1234/v1.

  4. Droid CLI

    Point Droid at the endpoint.

    Install Droid CLI on workstations. Set customModels[].baseUrl in ~/.factory/settings.json. Airgap mode refuses to start without a custom model configured.

Factory DroidPart II · Configuration
Restricted
Configuration

One file. Three lines that matter.

The Droid CLI reads a single JSON file at ~/.factory/settings.json. The three lines that matter are the base URL, the model identifier, and (optionally) a key. Everything else is defaults.

Three endpoints you will use

  • http://localhost:1234/v1
    LM Studio
  • http://localhost:8000/v1
    vLLM
  • http://localhost:11434/v1
    Ollama

All three speak the OpenAI Chat Completions protocol. Droid treats them identically.

// ~/.factory/settings.json
{
  "customModels": [
    {
      "model":        "qwen3-235b-a22b",
      "displayName":  "Qwen 3 · 235B · internal",
      "baseUrl":      "http://gpu-01.lan:8000/v1",
      "apiKey":       "${INTERNAL_VLLM_KEY}",
      "provider":     "generic-chat-completion-api",
      "maxOutputTokens": 16384
    }
  ],
  "telemetry": {
    "endpoint": "http://otel.lan:4318",
    "external": false
  }
}

Inference · Option A

LM Studio — evaluation.

A graphical, operator-friendly local inference server. Ideal for proof-of-value.

When this is the right choice

  • Evaluation phase — stand up a model in minutes with a GUI.
    yes
  • Small teams, moderate concurrency (one to five users).
    yes
  • Operators who prefer not to script CUDA, Python, or GPU scheduling.
    yes
  • Rapid model swap during a proof-of-value exercise.
    yes
  • A desktop-grade environment adjacent to the GPU.
    yes
Point your SDK calls at localhost:1234 instead of api.openai.com. Your application runs against a model that never leaves your machine. — LM Studio documentation

Limits to be aware of

  • GUI-first — not ideal for headless, rack-mounted servers.
    limit
  • Lower throughput than vLLM at high concurrency.
    limit
  • Less flexible on tensor-parallel schemes across many GPUs.
    limit
  • Proprietary licensing — defer to your legal office.
    limit

Recommendation

Use LM Studio for the proof-of-value phase. Its GUI lets security and operations staff see what is running, confirm model identity, and watch requests in real time.

Inference · Option B

vLLM — production.

The reference backend for an air-gapped Factory Droid cluster at team or department scale.

Why vLLM for the real deployment

  • PagedAttention — two to four times the throughput of naive servers.
    throughput
  • Continuous batching serves many developers in parallel.
    concurrency
  • Tensor-parallel across 2, 4, or 8 GPUs with one flag.
    scale
  • INT4, INT8, FP8 quantisation — all out of the box.
    precision
  • Apache 2.0 licence — no commercial-use ambiguity.
    licence
  • Serves entirely from local disk — the canonical air-gap backend.
    isolation

Run as a systemd service on the GPU host. Expose over the internal LAN only. Point every developer workstation at the same cluster through the baseUrl field.

# Launch Qwen 3 235B on 4× H100 80 GB
# INT4 fits in ~140 GB; TP=4 splits across cards

vllm serve /models/qwen3-235b-a22b-int4 \
  --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 32768 \
  --quantization awq \
  --host 0.0.0.0 \
  --port 8000 \
  --api-key ${INTERNAL_VLLM_KEY}

# Verify from a workstation
curl http://gpu-01.lan:8000/v1/models \
  -H "Authorization: Bearer $KEY"
Listing 02 One command, deterministic, scriptable — hundreds of requests per minute.

    density
  • H100 over A100 — FP8 and twice the memory bandwidth matter for first-token latency.
    bandwidth
  • Single node keeps tensor-parallel over NVLink and avoids slow inter-node fabric.
    topology
  • Four, not eight — the sweet spot for cost per developer; 8× is 2× the money for < 2× the throughput.
    economics

Capacity planning

One 4×H100 node comfortably serves 15 to 30 concurrent developer sessions on a 100–235 B model with vLLM continuous batching. Add a second node when p95 time-to-first-token exceeds two seconds.

Definition

The system around the model.

An agent harness is the full software system surrounding the LLM — the prompt scaffold, the tools, the context strategy, the verification loop, the policy layer, and the memory. The LLM is one component. The harness is what turns a component into a working engineer.

If you're not the model, you're the harness. — widely cited across 2026 harness literature

Why this is relevant to you

You will not run the largest frontier model — you will run a pinned, audited, open-weight model. The quality of the harness around it determines whether that model behaves like a frontier engineer or an unreliable intern.

Factory DroidPart III · Droid internals
Restricted
Droid Internals

Six places where Factory has done the engineering.

  1. Context Engineering

    Just-in-time retrieval and aggressive compaction.

    The LLM only ever sees the slice of the repository relevant to the current step — never the whole codebase. This lets a 32K-context local model behave like a 1M-context frontier one.

  2. Disciplined Tool Surface

    Fewer than ten tools, each one deliberate.

    Read, write, grep, run tests, inspect diff, open PR. Each tool is designed to minimise ambiguous outputs, so a smaller model routes correctly without needing to disambiguate.

  3. Deterministic Verification

    Every output passes a non-LLM gate.

    Syntax parse, type check, test run, lint — all deterministic. Catches hallucinations before they reach the human, which is the failure mode smaller models produce more often.

  4. Planner / Executor split

    Think once, execute many.

    A plan is formed up front and then executed with cheap tool calls. The expensive reasoning step is spent where it matters — not repeated on every subtask.

  5. Policy and Approvals

    Human gates where you place them.

    Which actions auto-run, which require review, which are forbidden — all enforced by the harness, never left to the model. Compliance is a configuration file, not a trust exercise.

  6. Local Observability

    Every token logged, locally.

    OpenTelemetry traces land on your collector. You can replay any run, inspect any decision, prove any claim about what the system did — all without a vendor in the loop.

Rollout Timeline

Ninety days from decision to production.

Phase 1 · Days 0–30

Evaluation.

  • Install Droid CLI on three to five workstations
  • Run Qwen 2.5-Coder 32B via LM Studio on a workstation GPU
  • Pick two or three real engineering tasks
  • Measure: completion rate, review burden, time saved
  • Produce an internal technical report

Phase 2 · Days 30–60

Production trial.

  • Rack the 4× H100 server; wire into the internal LAN
  • Stand up vLLM as a systemd service
  • Point ten to twenty developers at the shared endpoint
  • Enable OpenTelemetry collection to your stack
  • Security runs packet captures during live sessions

Phase 3 · Days 60–90

Hardening & scale.

  • Formal air-gap verification report
  • Role-based approvals and policy configuration
  • CI integration — Droid as a reviewer bot
  • Capacity plan: add nodes as developer count grows
  • Hand off to operations with a run-book
