The integration gap · 02

CUDA source enters the build through a different project item

C/C++test scopes ClCompile items; CUDA files are compiled through CudaCompile

C++test boundary

Host C/C++ scope

C/C++test Professional scopes the familiar ClCompile extensions: .c, .cc, .cpp, and .cxx.

CUDA boundary

.cu uses CudaCompile

The CUDA build task is not a standard C++ compile item. The Bridge creates C++-recognizable companion inputs so C++test can analyze host-visible CUDA source.

vectorAdd.cu ── CudaCompile ──► nvcc (not in C/C++test scope) │ └─► Bridge mirror vectorAdd.cu.cpp ── ClCompile ──► C/C++test ──► findings mapped to vectorAdd.cu
This is a compatibility workflow around the existing analyzer, not a claim that C++test has become a native CUDA semantic analyzer.
Components · 03

A small adapter around installed engineering tools

One native CLI, one Visual Studio extension, one local rule pack

Native CLI

Prepare and run

pcb.exe is a .NET 10 NativeAOT win-x64 tool. It generates companion solutions, installs local rules, invokes analysis, maps findings, and runs supported tests.

Visual Studio extension

Bring actions into VS

The net472 VSIX adds Parasoft CUDA commands, activation and legal UI, rule selection, configuration management, Error List findings, and editor squiggles.

Local rule pack

CUDA guidance checks

Python rule scripts are generated into Parasoft RuleWizard files at build time. The source checks remain heuristic and are not a complete C++ front end.

The VSIX bundles the native CLI and ESL rule assets. It does not include Parasoft, CUDA Toolkit, the issuer, or a token-signing private key.
CMake path · 04

CMake prepares a Visual Studio analysis solution

Six steps from a CMake CUDA folder to mapped findings

1ConfigureUse the Visual Studio 2026 CMake generator and the customer's toolchain.
2Evaluate projectsRead evaluated MSBuild metadata, including CUDA and C/C++ items and properties.
3Capture host flagsUse nvcc --dryrun to collect host defines, include paths, and options.
4Generate companionsCreate analysis .vcxproj files and .cu.cpp source mirrors.
5AnalyzeRun C/C++test on the generated *-parasoft.sln.
6Map resultsWrite reports and findings JSON, then publish locations against original CUDA files.
Important: this is not native CMake-engine integration. Generate the companion solution first, then analyze that solution.
Source fidelity · 05

Keep host-side compiler context close to nvcc

The companion project mirrors what nvcc would hand to the host compiler

  • One companion project is produced for each CUDA project.
  • Each .cu is mirrored as .cu.cpp, usually as a hard link, with a copy fallback across volumes.
  • Definitions, include paths, forced includes, language options, and host flags come from evaluated build metadata and nvcc's dry-run.
  • Source maps bring findings back to the original .cu path and line.
  • The analyzer project is for analysis, not a replacement build target.
Profile behavior

Use the customer's installation

The per-user CUDA compiler profile is adapted from the locally installed Parasoft profile. ESL does not ship Parasoft's base compiler profile or engine.

Activation and authorization · 15

Separate the ESL token from the Parasoft entitlement

Stage 1
30 days
Starts at first successful activation, not at token issuance.
Stage 2
+30 days
Its own period begins when the later stage is activated.
Stage 3
Permanent
No time limit. This does not promise perpetual support.

ESL activation controls

ECDSA P-256 signed tokens, machine binding, versioned DPAPI-protected local state, stage/replay checks, grace handling, and rollback detection.

Parasoft checks are separate

Protected operations validate a genuine Parasoft-signed cpptestcli and run a checked-source analysis probe. An ESL token cannot grant Parasoft features.

Local controls provide tamper resistance, not unbreakable protection. A local administrator can bypass or remove local state; no server-backed revocation is claimed.

Boundaries · 20

What this evidence does not establish

  • It does not prove complete C++ or GPU semantic analysis, full repository coverage, or compliance with CUDA guidance.
  • It does not convert CUDA guideline heuristics into MISRA checks. They are separate analysis layers.
  • It does not show CMake-native analysis or CMake-folder GoogleTest coverage.
  • It does not include device-kernel coverage or guarantee findings are true defects.
  • It does not establish Parasoft approval of the profile patch or rule generation.
Requires your own licensed Parasoft C/C++test Professional for Visual Studio. The Bridge is an independent ESL product; no approval or endorsement by Parasoft, NVIDIA or Microsoft is claimed.
