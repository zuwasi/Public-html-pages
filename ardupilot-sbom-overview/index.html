1Purpose and Intended Use of This Report

This document is not the SBOM itself. It is a pre-scan briefing: a map of what lives in the ArduPilot repository and what the SBOM tools provider needs to enable so the resulting SBOM is complete enough for an FDA premarket cyber device submission under Section 524B of the FD&C Act.

Key instruction to the provider
ArduPilot is a source-only project with no package manager manifest for its embedded dependencies. A package-manager-only scan will miss most of the third-party inventory. Scanning must combine recursive Git submodule resolution with vendored-source fingerprinting, and the final SBOM must describe the configured production binary (board, vehicle, feature set), not just the whole repository.
Before generating the production SBOM
Pin the exact release tag of ardupilot that the device firmware is built from, run git submodule update --init --recursive, and record the commit SHA of every submodule. All figures in this report describe the current master branch and must be regenerated for the exact submission revision.

5Hardware Platforms, HAL and RTOS Mapping

The build target determines which RTOS, toolchain, and driver set enters the binary. The provider needs to know which platform family the medical device uses so reachability analysis can be scoped to that configuration.

SITLNative host process (Linux / macOS / WSL)Software-in-the-loop simulation; typically part of the verification environment, not the shipped device.
LinuxPOSIX Linux SBC targets (BeagleBone, Navio, Navigator class)Full Linux userland stack applies.

The AP_HAL layer (libraries/AP_HAL) defines scheduler, threading, UART/SPI/I2C/CAN, GPIO, RC, storage, and timing interfaces. Board-specific feature selection matters: constrained boards compile out features, so two binaries from the same source tree can have different component inventories.

7Scripting and Middleware Components

ComponentRole and SBOM treatment
Lua scriptinglibraries/AP_Scripting embeds a customized Lua 5.3.6 interpreter with generated C++ bindings. User scripts load from SD card (APM/scripts) or are embedded into ROMFS at build time. Deployed Lua scripts must be inventoried and hashed separately from the firmware binary, because scripts can change runtime behavior without changing the binary.
MAVLinkMessage definitions from the modules/mavlink submodule; headers generated at build time into libraries/GCS_MAVLink/include/mavlink/v2.0. This is the primary external command, telemetry, and ground-control interface. MAVLink 2 supports message signing; command authorization is a system-level control to assess separately.
DroneCAN / libcanardCAN peripheral ecosystem: DSDL type definitions, libcanard embedded transport, AP_Periph node firmware.
DDS / ROS 2Micro XRCE-DDS client and Micro-CDR serialization; ROS 2 integration tooling under Tools/ros2.
lwIPEmbedded TCP/IP networking stack (submodule).

If MAVProxy (or any GCS) ships with or verifies the medical device, generate a separate SBOM from its own repository and Python environment.

8Licensing Overview

The main work is GNU GPL version 3 (see COPYING.txt). Third-party components retain their own licenses; there is no repository-wide exception that converts all embedded third-party code to GPLv3.

License scan configuration

  • File-level and nested-directory license discovery, not just a root LICENSE read.
  • Preserve per-file notices and scan nested LICENSE / COPYING files and the actual submodule repositories.
  • Expect a mix: GPLv3 first-party code; MIT (Lua), and mixed permissive/ LGPL-type terms in ChibiOS, lwIP, littlefs, CMSIS, gtest, gSOAP, and protocol libraries. Each needs an individual conclusion.

Why this matters for a medical device

  • GPLv3 distribution of modified firmware triggers corresponding-source obligations; "User Product" provisions can trigger installation-information obligations.
  • GPLv3 warranty and fitness disclaimers do not satisfy medical-device assurance obligations.
  • Whether higher-level proprietary software can remain separate from the firmware is a derivative-work and linkage question requiring legal review, not a scan result.

9Scan Module Configuration Checklist for the Provider

Enable the following modules and data sources when configuring the toolchain for this repository:

  • Recursive Git / submodule analysis, recording URL and exact commit SHA for each of the 15 submodules (plus nested submodules inside them).
  • C/C++ source composition analysis including conditional compilation (#if feature switches) and static linking into firmware images.
  • Python analysis for the Waf build system, code generators, autotest, and any shipped host-side tools.
  • Lua analysis, covering both the vendored interpreter (AP_Scripting/lua) and every deployed SD-card or ROMFS script.
  • RTOS / OS module scanning for ChibiOS, and FreeRTOS / ESP-IDF, Linux, or QURT as applicable to the device build.
  • Embedded library fingerprinting for vendored source copied under libraries/, where no package manifest exists.
  • License discovery at file and nested-directory level, with per-component license conclusions.
  • Firmware / binary scanning of the exact generated .elf, .bin, or .apj, including compiler and linker provenance (toolchain identity belongs in the SBOM).
  • Hardware-specific reachability analysis using the production board, vehicle family, and feature configuration so unused drivers are marked accordingly.
  • Separate host-tool SBOMs for the compiler/toolchain, Waf/Python environment, MAVProxy or other ground stations, ROS 2 tooling, and CI containers where these participate in production or verification.

11FDA Submission Considerations

Scope of this analysis
ArduPilot is mature, widely deployed autopilot software, but it is not automatically medical-device qualified. Reusing it in a device makes it software of unknown provenance (SOUP) that the manufacturer must evaluate under its own quality system.
  • Section 524B (cyber devices): the submission SBOM must cover the shipped firmware image, its build/toolchain provenance, and every third-party component in it, with plans and evidence for postmarket vulnerability monitoring against this inventory.
  • Intended-use and traceability: the manufacturer remains responsible for intended-use analysis, requirements traceability, hazard controls, cybersecurity risk analysis, V&V, configuration control, and postmarket monitoring. An SBOM supports but does not replace these.
  • Pin and freeze: record the ArduPilot release tag, submodule SHAs, toolchain version, board hwdef, and vehicle configuration that define the shipped binary. Regenerate all metrics from that exact revision.
  • Companion software: ground stations, companion computers, and build/verification containers get their own SBOMs; do not infer them from this repository.
  • Reproducible metrics commands for the pinned revision:
git submodule update --init --recursive
./waf list_boards | tr ' ' '\n' | sort -u | wc -l
find libraries/AP_HAL_ChibiOS/hwdef -name hwdef.dat | wc -l
cloc --exclude-dir=.git,build .

Report both "repository including submodules" and "first-party tree excluding submodules" component counts in the SBOM summary.
