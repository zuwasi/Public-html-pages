The useful question

What can this laptop achieve, and does extracting only three fields outperform lazy object access?

The upstream improvement

fields= already exists in fastsimdjson. It projects selected paths instead of returning document views.

The current upstream documentation reports 78 GB/s vs 61 GB/s on its server comparison. These are not our measurements.

What this study does not claim

We did not invent projection or write a faster parser. We reproduced the workload, compared two existing APIs, and measured the result on different hardware.

Different CPUs, versions and reporting statistics mean the server and laptop figures are not directly comparable.

The first obstacle

Windows had standard Python 3.14. WSL had Python 3.12. Neither was free-threaded.

Installed a separate 3.14.8t interpreter and virtual environment under the Linux filesystem. Verified the GIL stayed disabled after importing fastsimdjson.

Isolation has a boundary

Dependencies and files were isolated. CPU time was still shared with other Windows and WSL work. No power-plan changes, process termination or exclusive core allocation.

05 Implementation

Change what crosses into Python

Before · lazy document views
fastsimdjson.map_many(
    count_lazy,
    data,
    format="lines",
    threads=24,
    lazy=True,
)

The callback reads event["type"], then traverses nested views for opened pull requests.

After · projected scalar tuple
fastsimdjson.map_many(
    count_fields,
    data,
    format="lines",
    threads=24,
    fields=[
        "/type",
        "/payload/action",
        "/payload/pull_request/base/repo/language",
    ],
)

The callback receives (type, action, language). fields= replaces lazy=True; they cannot be combined.

What stays the same: one Python callback per event, per-thread counters, final counter merging, and the unused map_many return-list overhead.

06 Protocol

One input. Ten configurations. Seventy checks.

01

Load

Download, decompress and join all eight files before timing.

02

Establish truth

Decode every event with the independent standard-library implementation.

03

Warm up

Exercise both APIs at every thread count and verify those counters.

04

Time and compare

Seven shuffled rounds. Check every result against the complete reference.

Inside the timer

Parsing, selected-value conversion, Python callbacks, counting, disposal of callback results, and merging counters.

Garbage collection enabled; explicit collection runs before each timer. One process, 1 / 4 / 8 / 16 / 24 worker threads.

Outside the timer

Network transfer, storage reads, gzip decompression, reference calculation, warmup, and correctness comparisons.

Report the median, retain every individual timing. GB/s uses decimal input bytes, not physical memory traffic.

Do not confuse the percentages

Throughput is bytes divided by time. A 24.8% throughput increase corresponds to a 19.9% time reduction, not 24.8% less time.

This is an in-memory workload result, not an application-wide speedup or a disk-ingestion guarantee.

11 What went wrong

Files were isolated. CPU contention was not.

First session · excluded

A concurrent .NET build started during the benchmark. WSL became heavily CPU-contended, and timing variation increased substantially.

We left the other work untouched. Those performance numbers are not used in this presentation.

The first session’s raw samples were not retained. Its exclusion is documented in the public report.

Second session · published

Waited until three consecutive five-second CPU samples were below 15% busy, then repeated the entire benchmark.

The charts use only that second session’s 70 timings. All counts passed again.

The host remained shared. We did not establish controlled power, thermal or frequency conditions.

Other limits worth keeping beside the headline

One dataset; no orjson/msgspec comparison here; no end-to-end ingestion timing; no confidence interval; no claim that AVX2 on a laptop should match AVX-512 on a 64-core server.

12 Practical use

Use projection when most of the document is irrelevant

A good fit

  1. Large NDJSON streams and only a few known fields.
  2. Free-threaded Python, with compatible extensions.
  3. Per-worker aggregation instead of shared hot counters.
  4. A thread-count sweep on the actual target machine.

On this machine, 24 threads was fastest among the five settings tested.

Check before adopting

  1. fields= returns None for missing paths by default; lazy indexing can raise.
  2. Only request scalars if that is all you need; selected objects are materialized.
  3. Disk or decompression may dominate your real pipeline.
  4. On ordinary GIL-enabled Python, this library does not gain the same threaded parallelism.

The lesson: first reduce unnecessary Python object creation. Then measure parallelism, correctness and the full application separately.

14 Next experiment

Native counting is an opportunity, not a result

Measured and complete

16.07 GB/s

Median with existing field projection.

Same input, same answers, 24.8% higher throughput than lazy views at 24 threads.

No custom parser or extension changes were needed.

Proposed, not implemented

Move extraction and per-worker counting into native code, returning only the final counters to Python.

This could remove millions of Python callbacks, temporary tuples and unused callback-result entries.

No speedup is claimed. It needs a prototype, equivalent validation/error behavior, and a fresh benchmark.

Our contribution

A reproducible local experiment, an independent correctness reference, transparent timing samples, and a measured recommendation for this workload on this hardware.
