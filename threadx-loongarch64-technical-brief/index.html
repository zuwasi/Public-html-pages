What was built

Eclipse ThreadX had no LoongArch port and no BSP for any Loongson board. The project added both, without touching the kernel:

LayerLocationContent
Port ports/loongarch64/gnu/ 7 assembly files and 3 C files: context save and restore with full integer and FP state, scheduler, atomic interrupt posture via csrxchg, stack build, tick, freestanding memcpy/memmove/memset/memcmp.
BSP bsp/qemu_virt/ Reset entry, linker script with a stack guard, constant timer, NS16550 UART with interrupt-driven receive through PCH-PIC and EXTIOI, fatal handler, test exit.
Kernel external/threadx/ at v6.5.2.202603_rel Eclipse ThreadX as a pinned submodule. 0 kernel lines changed across 17 commits.

The port was derived from the upstream RISC-V64 port, not a MIPS port: LoongArch is its own ISA (no CP0, no delay slots, CSR-based traps), and ports/ contained no MIPS port to start from. All CSR and IOCSR access lives in assembly, so C contains no inline assembly (MISRA C:2025 Dir 4.3).

How it was verified

  • Bring-up images on QEMU. Seven test images (timer and interrupt posture, fatal exception, memory functions, long idle, relinquish, UART RX interrupt, 8-thread demo with FP context checks) run under qemu-system-loongarch64 -M virt -cpu la464 with exit code as part of the verdict.
  • Upstream regression suite. The vendor's own test suite built for LoongArch and run on QEMU, 96 tests × 6 kernel configurations (default, optimized, stack checking, random fill, trace, no notify callbacks): 576/576 on every push.
  • CI matrix. 8 GitHub Actions jobs on Ubuntu 24.04: Debug and Release builds with QEMU tests, a freestanding-libc check (nm -u empty, closing deviation DEV-001), and one job per kernel configuration.
  • Tool confidence. Parasoft C/C++test classified as a T2 tool per IEC 61508-3 7.4.4 and validated with 8 seeded violations, 8/8 detected.

MISRA C:2025 with Parasoft C/C++test

The analysis is wired to the real build: a GCC 14 LoongArch64 compiler model, cpptestcli -trace over the actual CMake/Ninja build with the product's exact flags (-march=loongarch64 -mabi=lp64d -msimd=none -ffreestanding -nostdinc), so findings match what ships. Five scans over two days took ESL code from 143 baseline findings to 0; every remaining suppression names a deviation record (DEV-001 to DEV-015) with rationale, risk analysis and approval status. The upstream kernel was analysed report-only: 613 findings across 19 guidelines, 0 Mandatory, triaged for focused review rather than claimed as compliant, because modifying ThreadX would fork it.

The compliance summary, dashboard and traceability are generated by scripts in tools/ from the SARIF reports and the deviation records, so the evidence is regenerable, not hand-written.

Structural coverage

SIL 3 makes statement and branch coverage highly recommended (IEC 61508-3 Table B.2). Parasoft cpptestcc instruments only ESL-owned port and BSP C files; the coverage runtime emits frames as ASCII hex on QEMU's UART, decoded by collect_coverage.py. Result: 92% line coverage, with the 16 uncovered lines individually justified (measurement limit, failure paths, defensive code) and statement/branch/MC/DC reports listed as open items deferred to the audit phase.

The four days

  • Day 1: freestanding build, tx_port.h, MISRA enforcement plan, safety plan and requirements committed before any port code; QEMU BSP and bring-up tests in CI.
  • Day 2: context frames, scheduler, 8-thread demo; upstream regression 576/576 after fixing one defect found by the port analysis; MISRA scans 143 → 0.
  • Day 3: compliance dashboard, UART RX interrupt route verified against QEMU source, memory/idle/relinquish tests, coverage on target, kernel gap analysis.
  • Day 4: design record, compiler behaviour record, safety manual, traceability generator, verification report, release package, full re-validation, tag v1.0.0-rc1, CI 8/8 green.
What four days did not produce. Human approvals (deviation records need the technical lead and safety manager; signed git tags will confirm them), independent reviews, statement/branch/MC/DC coverage reports, real silicon (everything ran on QEMU 8.2.2), and no independent assessment. This is an evidence package, not a certificate, and the release notes state all of it as open.
