Fil-C vs MISRA C/C++ on 78 real bugs

Case file 01 asked whether Fil-C beats a MISRA C compliance process on a hand-built 5-bug suite. It did not: Parasoft caught 5/5 at build time, Fil-C caught 3/5 at runtime and silently missed both off-by-one overflows. The obvious objection: synthetic bugs are too easy. So we ran the same fight on real-world bugs: 78 accepted bugs from the SWE-sweep dataset, in five real open-source repositories, fixed by their maintainers in real commits.

78 real bugs 5 real repos full methodology, redo it yourself

Dataset: SWE-sweep (swesweep.com), real fix commits from 14 widely used C/C++ projects. Toolchain under test: Fil-C 0.687 (pizlonated Clang 20, Filip Pizlo). Baseline toolchain: gcc 13. Analyzer: Parasoft C/C++test, Flow Analysis + MISRA C 2025 (C repos) / MISRA C++ 2023 + CERT C++ (C++ repos), whole-project scan. Companion deck: case file 01, Fil-C vs MISRA C.

02 / the claim under testcase file 02

The claim: swap the compiler, get memory safety

Fil-C's promise. Recompile existing C/C++ with Fil-C and every forbidden memory operation stops the program instead of silently corrupting it. No rewrite, no Rust migration, no opt-out. Buffer overflows, use-after-free, double free, invalid dereference: contained.
The implied conclusion. Changing the compiler is cheaper than rewriting, so the memory-safety problem of C/C++ is solved, and the Rust migration argument (and implicitly, the compliance toolchain argument) loses its force.
What the claim does not say. Fil-C does not find bugs. It lets a memory bug crash instead of exploit, when the buggy path executes. Logic bugs stay untouched. And for the people who actually write C today (automotive, avionics, medical, regulated industries), the process is MISRA compliance verified by static analysis. That process claims to find and fix the bug before release.
So we measured both jobs on the same real bugs. Not opinions. Same 78 defects, same repositories, two strategies, one scoreboard.
03 / methodcase file 02

The experiment

The bugs are real. 78 accepted bugs from the SWE-sweep dataset: each one is a defect that was actually introduced, shipped, and fixed by the maintainers of a widely used open-source project. We take the pre-fix commit as ground truth.
The repos are real. The five smallest from the dataset: libexpat (9 bugs), jerryscript (15), micropython (22), z3 (11), proj (21). Three C, two C++. Over 392,000 lines of first-party code in total.
The QA loop is real. Build each repo at the pre-fix commit with gcc, run its own test suite: everything passes, the bugs are silent. Rebuild the identical tree with Fil-C 0.687, run the same suite, count filc panic events. This is exactly how an adopter would experience Fil-C.
The analyzer runs as in practice. Parasoft C/C++test scans the whole buildable project (compile-commands driven), Flow Analysis plus MISRA C 2025 for the C repos and MISRA C++ 2023 + CERT for the C++ repos. No hints, no bug list, one scan.
Honest note. Fil-C's net only fires on executed paths, and the suites do not reach the 78 defect sites. That limitation is itself the finding: in normal operation Fil-C delivers zero detections, and logic bugs are outside its model even with perfect coverage.

Every one of the 78 bugs was classified by defect mechanism in three independent passes (two blind, one adjudicated with full pre-image context). Roughly two thirds of real bugs are logic and contract bugs: they compute the wrong answer while staying perfectly memory-safe. A memory-safe runtime, any memory-safe runtime, simply has no opinion about them. That is the structural reason a compiler swap cannot replace a static analysis process.

08 / strategy comparisoncase file 02

Three strategies, one budget conversation

A. MISRA compliance, verified with Parasoft. One scan finds 52 of 78 before release, no execution, no coverage needed. Fix them and the residual is 26 bugs, of which only 9 are memory-class. The process also produces the audit trail certification actually asks for.
B. Fil-C. Found 0 in normal operation. Best case, with a fuzzer that reaches every defect site, it can contain the 20 memory-class bugs and none of the other 58. As a substitute for A, strictly weaker on every dimension we measured.
C. A, then B. The honest best: fix the 52, then let Fil-C sit under the remaining code. If one of the 9 residual memory bugs is ever reached in the field, it becomes a controlled panic instead of an exploit. That layer is worth about 12% of the original bug population, on executed paths only.
The asymmetry that decides it. Strategy A's value requires fixing findings (a management decision). Fil-C's value requires nothing but a build. But A's value is 52 bugs fixed now, evidence forever; B's value is a safety net for the residue. Different tools, different jobs, and the primary job is detection.
09 / the migration taxcase file 02

What "just recompile with Fil-C" costs in practice

micropython under Fil-C 0.687, ports/unix
$ make CC=filc ... MICROPY_PY_FFI=0
builds ok, then any test that lands on nlr_push:
filc safety error: cannot handle inline asm
$ ... retry with -DMICROPY_NLR_SETJMP=1 (setjmp fallback)
Fatal error in LLVM pass: FilPizlonatorPass
  while compiling py/nativeglue.c (-O0)
verdict: Fil-C 0.687 cannot run micropython
Every dependency must be rebuilt. proj links sqlite3, and Fil-C rewrites sqlite3 calls into pizlonated_sqlite3_* symbols that only a pizlonated sqlite provides. We compiled the sqlite3 3.45.1 amalgamation with Fil-C ourselves to make proj link. A static analyzer never asks this.
Inline asm is a wall. Embedded and systems code leans on it; Fil-C refuses it at runtime, and its setjmp fallback crashed the Fil-C compiler itself.
Build times balloon. z3 took about 50 minutes and produced a 268 MB instrumented test binary; proj about 35 minutes plus the sqlite3 detour. Every CI run pays this again.
Meanwhile the MISRA route needs zero code changes to start. Point the analyzer at the build, get findings the same day, fix what you accept, document deviations for the rest.

The genuine strength of the agent mode is novel discovery beyond the known bug set, which is complementary, not a substitute for qualification-grade static analysis.

11 / verdictcase file 02

So: MISRA compliance, or Fil-C?

As the primary tool: MISRA compliance + Parasoft, decisively. 67% of real bugs found before release versus zero, wider scope (logic and contract bugs included), lower adoption cost, and certification evidence that safety standards actually require.
As an optional second layer: Fil-C is legitimate. After the code is clean, its runtime net covers the memory-class residue: here, 9 bugs out of 78, about 12%, converting silent corruption into controlled crashes on executed paths.
Fairness, stated plainly. Fil-C is a containment compiler, not a bug finder, and it never claimed otherwise. Our zero is measured the way adopters would experience it (build + existing QA); a fuzzing campaign under Fil-C would fire some of the memory subset. That is the comparison the industry needs: containment is not detection.
The deeper point. For the people who write C today, in regulated industries, the question was never "Rust or Fil-C". It is: does the release ship with named, fixed, documented defects? Static analysis answers that.
